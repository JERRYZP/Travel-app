## 〇、一句话方案

首页从「提醒任务列表」改成「行程状态墙」：**按出行日一行行列出这趟要去的地方，每个地方标清楚票抢到没有**。提醒功能一条不删，但首页的主心骨从“什么时候动手”换成“这趟成了没”。

为什么值得改——旧首页有三个结构性空缺：

1. **结果空缺**：产品的职责到“提醒发出”为止，票到底抢没抢到只有用户自己知道。而调研里用户最焦虑的恰恰是这一段（“一次没约上故宫，整个行程的记忆基调都被改写”）。
2. **残缺空缺**：7 个不用预约的景点（北海、天坛这类）进不了首页，用户看到的“行程”是缺的，还得自己另记备忘录。
3. **散乱空缺**：多条提醒散在多个放票日里，用户答不出“我这趟约上几个了”。

另外，放票日轴的首页在抢票期之外是空的；行程轴全年都有内容——这是“行程凭什么当首页”的根本理由。

## 一、定位与主轴（已确认）

- **定位不变：帮用户把票抢到手。** 一个功能若不回答“这张票到手没有 / 怎么让它到手”，就不做。路线、交通、餐厅、攻略、AI 推荐仍然出界。
- **主轴必换**：首页按出行日组织，放票时刻变成每个行程项上的一行属性。
- 这与产品文档现有原则冲突（P-002“时间线优先、以放票时间轴组织信息”；P-003“提醒事件是最小执行单元”）。改写方向已确认，**待开发启动时与产品文档、CLAUDE.md 一起同步修订，本阶段不动需求之外的文件**（见第十一节）。

## 二、首页形态与行程边界（已确认）

### 2.1 单形态

只有行程状态墙一种首页，不做视图切换，不保留“按放票时刻”的独立入口，也不保留“提醒任务 / 添加提醒”双 Tab。

理由：两种视图并存会让用户每次进首页先选一次，且两边排列对不上、看起来像数据错了。提醒任务仍存在，但退到行程项内部，不再作为用户的一级页面。

### 2.2 无行程时

显示创建引导空状态，沿用 UI-009。

### 2.3 多行程分段墙

多行程不设切换 Tab，也不做“每个行程一张摘要 Banner”。所有未结束行程按日期顺序纵向呈现；每趟行程一个分段标题（城市 + 日期范围 + 紧凑进度 + 右侧行程管理入口），下面是它的行程项。分段标题在该行程区间内吸顶。只有一趟行程时，分段标题弱化，看起来就是一堵干净的墙。

**行程拆分 / 合并规则沿用 TRIP-RULE-002：**

1. 同城市，且两个日期范围**有交集或首尾相接**，属于同一行程。
2. “首尾相接”＝前一行程结束日的次日，正好是另一个行程的开始日。
3. 中间至少空一天，则属于新的独立行程。
4. 示例：`10月1日–7日` 后新增 `10月8日–9日`，合并为同一行程；新增 `10月10日–12日` 则为新行程。
5. 行程按开始日期升序排列。页面上可以同时存在多个进行中/未来行程分段，但不做行程切换 Tab。

**行程结束与历史：**

- 结束日当天仍属于进行中行程，用户仍可回看和标记结果。
- 结束日次日北京时间 0 点起归入历史行程。
- “是否结束”在读取时按 `endDate` 与北京时间计算，不依赖后台定时任务落状态。
- 历史行程不支持跨城市；将来做跨城市时，如果不同城市日期可重叠，必须重新设计分段规则。

### 2.4 顶部摘要与吸顶横幅

- 整个首页只有一张完整摘要卡，默认展示**最近的进行中/未来行程**：行程名 + 日期 + 倒计时 + “门票搞定 N/M”。
- 其他未来行程不重复完整摘要卡，只在分段标题上显示日期、紧凑进度和管理入口。
- 两趟行程只隔一天时，不插空档日，也不切换横向 Tab；直接按时间顺序进入下一分段。
- V1 不做横向行程 Tab，也不做横向锚点导航条。只有未来出现 ≥3 个高频并行行程时，再评估“点击滚动到分段”的锚点目录，仍不得隐藏页面内容。
- 吸顶放票横幅跨全部当前/未来行程取全局最近的 1–2 个放票时刻，不按行程分开计算。

## 三、行程项与状态（已确认）

**行程项 = 哪个行程 + 哪个景点 + 哪一天。** 一个景点可以加多天（备选），就是多个行程项，各有各的状态。不做“日期待定”的半吊子状态——“哪天都行”靠多加几项表达。

同一景点的多个备选日期通过 `backupGroupId` 归为一组，用于结果收束、门票进度和挽回建议。

### 3.1 六个用户可见状态

| 状态 | 触发条件 | 备注 |
|---|---|---|
| 待抢 | 还没到放票时间 | 含“已设提醒”与“未设”，用户眼里都是“还没到点” |
| 可抢 | 放票时间已到，且 24 小时内未标记结果 | 页面上最醒目的行动状态，必须持续提供官方预约入口 |
| 已成 | 用户标记“抢到了” | 人工结果，不可反复修改；仅允许短时撤销误触 |
| 未成 | 用户标记“没抢到” | 人工结果，不可反复修改；仅允许短时撤销误触 |
| 未标记 | 放票后超过 24 小时仍未标记结果 | 中性态，不判失败；到行程日结束前仍可补标记和预约 |
| 免预约 | 景点无需预约 | 随到随玩，不进入提醒流程 |

### 3.2 状态计算与数据口径

- **只持久化用户结果**：`result = SUCCESS | FAILED | 空`。
- `待抢 / 可抢 / 未标记 / 免预约`是展示态，按放票时间、当前时间和用户结果在读取时计算，不依赖定时任务写状态。
- `未标记` 不是人工终态。放票后超过 24 小时且没有用户结果时显示“开过票了”；到行程日 23:59 北京时间之前，用户仍可通过右侧菜单补标 `已成` 或 `未成`。
- 提醒送达状态单独记录，包括 `待提醒 / 已送达 / 未送达`，不得与票务状态混为一个字段。
- `可抢 / 未标记 / 未成` 状态都保留官方预约入口；入口不会因为 24 小时过去或用户标记失败而消失。`已成` 也保留查看/复制官方入口。
- 不做“已约满置灰”：V1 没有可靠余票数据，不编造可约或约满结论。

### 3.3 结果标记不可修改与短时撤销

- 人工标记 `已成` 或 `未成` 后，不允许任意反复改状态，保证状态稳定。
- 每次标记后允许 **4 秒内撤销一次**，用于处理误触。
- 撤销交互使用页面底部轻量 Snackbar，不使用系统 Toast 或弹窗。文案示例：`已标记为抢到了 [撤销]`。
- 4 秒后入口关闭，结果成为最终人工记录。
- 网络失败时回滚前端状态并提示，不静默假装成功。

## 四、回填：用户标记结果（已确认）

原则：**回填是用户给产品帮个忙，不是用户的义务。** 不追问、不做表单、满屏不弹气泡。

### 4.1 标记入口

- 标记入口**只在行程卡片上，不进景点详情浮窗**。详情浮窗只做预约直达（放票倒计时 + 官方入口），两个气泡（“抢到了 / 没抢到”）是行程卡片的能力，与浮窗无关。
- **主入口 = 首页行程卡片的气泡**：开票时间过后，已开票且未标记的行程项卡片上展示“抢到了 / 没抢到”两键（即“可抢”状态的动作区）。
- 用户点提醒卡片（或短信短链）进入小程序后，先落到对应景点的详情浮窗（预约入口 + 倒计时，用户抢完票离开）；**等用户再次回到首页时，才在行程卡片上看到标记入口**。标记不在抢票前出现——开票前不问结果，开票后才出现。
- 多个已开票且未标记的行程项并存时，进入首页**自动滚动到最近应标记的一条**（优先“可抢”态，即还在 24 小时窗口内的）。
- **次入口**：未到“可抢”主动展示时机（如已过 24 小时转“未标记”），或想补标的项，右侧菜单内提供“标记结果”。
- 提醒发送失败、未触发、未送达时，不影响票务结果标记；行程项仍保留标记入口。
- 标记入口保留到该行程项 `visitDate` 的 23:59（北京时间）。
- 没有设置提醒的行程项同样可以标记结果。

### 4.2 抢到了之后（收束动线）

- 单日行程项直接完成标记，不追问日期。
- 同一备选组还有未处理日期时，在行程项旁显示一条内联提示：`已确认 10月2日去故宫，10月3日的备选 [删掉] [保留]`。
- 用户选择“删掉”：按删除规则二次确认后删除备选及其提醒任务。
- 用户选择“保留”或不操作：默认保留备选，且**继续按原计划抢票和发送提醒**。用户可能尚未最终确定行程，也存在抢到两个日期后临行前退掉其中一天的真实需求。
- **永不静默自动删除备选。**

### 4.3 没抢到之后（挽回动线）

**挽回建议（浮层）有固定入口**：状态卡片右侧菜单或卡片上提供“建议”入口，标记“没抢到”后浮层被误关也能随时重新打开，不能一次划掉就找不回来。

1. 同一天回流票 → **V1 不做**。无可靠官方数据源，宁可没有，不编一个。
2. **用户已设备选日期、且备选尚未到放票时间**：**不做任何提示，按计划提醒**。已有安排不打扰——备选的存在本身就是挽回方案。
3. **用户没设备选、但行程内有可用日期**：在挽回浮层中同时展示两类候选：
   - 已开票的可用日期：“已开票，去官方渠道预约 [立即预约]”（不承诺一定有余票）；
   - 未开票的可用日期：“10月4日 17:00 放票 [设提醒]”。
4. **用户没设备选、行程内也没有可用日期**（已过、闭馆、无放票规则）：**静默，不予任何提示**。此时不提供“延长行程”——延长出去的新日期同样无票可抢，等于空转建议。
5. **什么都不建议是合法的。** 失败时刻的空转建议比没有建议更伤信任。

规则：“没抢到”是人工结果；换天设提醒生成新行程项，与旧项并列。此时刻不放任何商业化占位。

### 4.4 数据用途边界

回填数据只用于产品洞察，**不回写难度分**。抢到是成就事件，抢到的人爱说话、没抢到的人沉默，直接拿来校准会把方向算反。

## 五、提醒推送与首页的分工（已确认）

- **抢票当天用户靠推送不靠翻首页**——推送点进来必须直达行动：落到对应行程项的详情浮窗，浮窗内有官方预约入口和放票倒计时。提醒是提前 N 分钟发的，点进来票还没开抢，必须告诉用户“20:00 开抢，请在此等待”。
- 用户自己回到首页时：24 小时内若有刚开抢、还没标记结果的行程项，自动滚到最近一条（优先“可抢”的——还来得及救；过时不滚）。
- 顶部**吸顶横幅**：全局最近的 1–2 个放票时刻 + 倒计时 + 直达，跨全部当前/未来行程取最近项。
- 删除“提醒任务”一级 Tab 后，**右侧菜单只放操作项**；状态类信息一律在卡片上直接展示，不进菜单：
  - 右侧菜单（操作）：标记结果；修改提醒设置 / 取消提醒；删除行程项。
  - 卡片直显（状态）：提醒状态（待提醒 / 已送达 / 未送达）以状态标签展示；**点状态标签（或其 icon）即查看详情**——未送达的看具体原因，已送达的看送达时间。
- **提醒未送达是状态，不是普通操作。** 行程项卡片上显示轻量警告 icon，并在文案上强调，例如“提醒未送达”；点击后查看具体原因。不能只藏在菜单里，避免重新出现静默失败。
- 附带好处（不作依据）：首页改拉取型后，用户重复进首页确认状态的行为可能减少，对订阅消息额度紧张的老问题或有缓解——只是可能，不写进验收。

## 六、删除动线（已确认）

- **删除层级**：删单个行程项 → 删某一天的全部行程项 → 某天删完后若整趟行程一项不剩，行程随之消失。
- 每步都二次确认，提示语写清连带范围，例如“该日期下的提醒会一并删除”。
- **“已成”的行程项**删除要二次确认——那是成果记录，误删可惜。其余状态同样必须先确认，不做无确认删除。
- 收束动线中删除备选日期，同样走二次确认。
- **旧规则修订**：现行“已送达的提醒保留为历史、不许删”与收束动线冲突。按新规执行，删除行程项时连带删除对应提醒任务，开发时同步修订产品文档。
- **行程删除的判定**看有没有行程项，不看还有没有提醒任务——否则只有免预约景点、没设提醒的行程会被误判成空的删掉。
- **提醒额度不退还**：删任务时微信那边的授权次数已经花掉，账本不回调。

## 七、加入行程与购物车（已确认）

- **一个入口（购物车），两种结果**：需预约景点按钮“加入提醒”，默认勾选提醒；免预约景点按钮“加入行程”，没有提醒勾选框（不是置灰，是压根没有），代之以固定说明“无需预约，随到随玩，不设提醒”——说明必须与按钮同屏可见。
- **免预约景点也走同一条时间线**：用户同样从排期时间线选择具体日期后加入行程，只是不生成放票时刻、不进入提醒流程。因此免预约行程项也一定带有 `visitDate`。
- **弱提醒规则以最新产品文档为准**：`remindable && difficultyScore <= 2` 的景点默认不勾提醒。当前为 11 个；代码按字段动态计算，不写死数量。购物车内仍可手动改。
- 提交通知：“已加入行程 · 其中 M 个已设提醒”。
- 免预约景点进首页的价值定位：**信息完整性、对冲过时攻略制造的假焦虑**（“到门口扫码就能进，真不用那么焦虑”）。不是新方向，不当卖点。
- 环球影城属于“需预约但无固定放票时刻”，V1 继续不可选、不可加入；后续是否从景点库删除另行决定。V1 不为它增加特殊状态。

## 八、V1 范围、摘要口径与节奏（已确认）

**做（10 项）**：

1. 首页行程状态墙（出行日轴、多行程分段、历史行程收纳）
2. 顶部行程摘要卡：行程名 + 日期 + 倒计时 + “门票搞定 N/M”进度条
3. 吸顶放票横幅
4. 六状态标签
5. 回填气泡两键 + 4 秒撤销 + 24 小时未标记中性态
6. 免预约景点进行程（含购物车分流）
7. 没抢到的挽回动线（第二、三层）
8. 删除动线（含二次确认）
9. 推送落地详情浮窗 + 首页自动定位
10. 删掉“提醒任务”一级 Tab

**门票进度口径：**

- 分母 M = 行程中去重后的**预约需求组**，不是提醒条数，也不是免预约项。
- 同一景点多个备选日期使用同一 `backupGroupId`，只算一个需求；任意日期“已成”，该需求即计入搞定数 N。
- 未设提醒但确实需要预约的景点仍进入 N/M，避免进度伪装成完成。
- 免预约项不计入 N/M，另起一行“另有 X 处随到随玩”。
- “已设提醒数量”如需展示，只作为购物车或次级统计，不冒充门票完成度。

**不做（V1 明确出界）**：放票日轴独立入口、视图切换、回流票建议、行程复盘分享、跨城市、退票/不去了、多城市管理、商业化占位。

**节奏：三步连做，中途不停闸**（已确认）。免预约进行程 → 状态标记 → 换新首页，连续推进尽早交付。每一步仍独立验收。

**历史行程收纳**：已结束的行程折叠在页面底部一行（“过往行程 (2) · 10月2日–5日 搞定 4/5”），点开平铺，卡片与主墙同款但整体灰化、无操作按钮（只能点进景点规则页回看）。历史区的“没抢到”不用红色——红色是行动召唤色，历史区的失败已无法挽回。行程结束的**次日**才归入历史。没有历史行程时该行整个隐藏。

## 九、数据红线（最高优先级，沿用）

1. **“纪念堂 12:38/12:50 补放”是虚构信息，审计已判定不可用**。**已于 2026-09-15 清理完毕**：4 份数据副本、对外总表（data.json + index.html）、0907 运营表、难度表均已移除；纪要 4.3 示例已改写；3 份历史快照文档已加勘误标记（保留原文存证）。遗留事项：已对外的 PDF（09-10 生成）无法撤回，index.html 已清理，需重新导出 PDF。纪念堂难度分已于 2026-09-15 重新评定为 3（用户确认），并从弱提醒名单移除，相关数据已同步。
2. 景点规则值只能来自**官方渠道公告**，不得来自攻略帖、舆情报告、社区文章、AI 生成报告。
3. 回流/补放信息入库必须三要件齐全：官方出处 + 明确有效期 + 到期降级说明。**无合格数据不建字段**——先建字段等于给虚构信息留容器。

## 十、怎么判断改版成功（验收）

**不看回填率**——北京景点热度和难度早有定论，回填样本又有偏（抢到的人爱说话），没有分析价值，回填率指标取消。看两个现成的数字：

1. **挽回动线的使用量**：标了“没抢到”的用户里，多少人点了“换 10月4日再约”这类建议——回填存在的唯一理由。
2. **“抢到了”的标记量**：用户是否真把首页当状态墙用，而不是当列表。

另外两项结构性收益独立成立、不依赖以上数字：全年首页有内容（不再只有抢票期热闹）、免预约景点补齐行程完整性。
