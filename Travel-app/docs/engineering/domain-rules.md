# Travel-app 核心业务规则

> 详细页面行为以 `产品文档.md` 为准，接口字段以 `API-契约.md` 为准。本文记录最容易在开发中改错的硬约束。

## 行程与进度

- 首页只有行程状态墙一种形态，不保留双 Tab、任务列表或视图切换。
- 行程按结束日读取时拆分：结束日当天仍属进行中，次日进入历史。
- 行程**全部结束**时摘要卡不退场：展示最近一段过往行程（`history[0]`），副标题显示「已结束」；只有全部结束才退化，还有未结束行程时仍是最近那趟未结束行程。历史折叠区照旧列出全部历史行程（`HOME-RULE-008`）。
- 摘要卡展示的行程（`summaryTrip`）与「新增提醒预填」用的行程（`primaryTrip`）是**两个字段**：前者可以退化成已结束行程，后者只允许未结束行程——混用会把过去的时间范围预填进 PAGE-005。
- 进行中行程内，已结束日期组默认折叠，入口置于该趟内容顶部、今天/未来日期之前；折叠不得按 `releaseAt` 判定，未来出行日即使已放票也必须保持展开。
- 同一时间刻度的多个提醒在摘要卡中合并为一颗胶囊；`limit` 数的是时间点，不是行程项数。
- 门票进度分母按 `backupGroupId` 去重；免预约项不进分母；需预约但未设提醒的项仍进分母。

## 行程只读分享

- PAGE-018 只分享首页 `primaryTripId` 对应的当前未结束整趟行程，不分享单条 `trip_item`、历史行程或多趟行程拼接页。
- `trips.shareToken` 是内部字段。普通 `trip.list` / `home.bootstrap` / 管理端只读响应不得携带原始令牌，只能暴露 `shareActive`。
- `tripShare.open` 只按 64 位十六进制令牌查询；公开投影是白名单，禁止输出 `userId/openId/tripId/itemId/releaseAt/result/ticketState/reminder`。
- 会话分享标题的应用内昵称只由主人接口 `tripShare.create/status` 返回；不得进入公开投影、分享路径或埋点。平台不开放真实微信昵称，资料缺失时回退「朋友」。
- 接收方展示全部日期和全部行程项，包括过去日期与同一景点多个备选日；不替用户挑选、合并或推导到访顺序。
- 链接在 `endDate + 7 天` 当天仍有效，次日起失效；停止分享或删除行程立即失效。停止、过期、删除和非法令牌统一返回 1042。
- 同城行程合并时，有效分享令牌迁到存续行程；多个候选冲突时优先存续行程自身令牌，否则取确定的首个候选。
- 只读页隐藏二次转发，不实现 `onShareAppMessage` / `onShareTimeline`，不渲染票务、提醒、菜单或景点动作。

## 票务状态

固定六态：

```text
PENDING / BOOKABLE / SUCCESS / FAILED / UNMARKED / NO_RESERVATION
```

展示文案：

```text
待抢票 / 可抢票 / 已约到 / 未抢到 / 待确认 / 免预约
```

判定顺序固定：

```text
免预约 → 人工结果 → 放票前 → 放票后 24 小时内 → 待确认
```

「人工结果」必须早于时间条件，否则已标记结果会被时间重新翻回待抢。页面不得自行重推状态。

人工结果只允许 `SUCCESS | FAILED`，4 秒内可通过页面底部 Snackbar 撤销。

## 提醒送达状态

- 票务状态与提醒送达状态分字段、分 UI 展示。
- 行程项提醒固定四态：`NOT_SET / WAITING / TRIGGERED / MISSED`，展示为未设提醒/待提醒/已提醒/未送达。
- `NOT_SET` 是开启提醒的入口，`MISSED` 是必须暴露的异常信号，不允许从卡片上删除该状态。
- `MISSED` 优先级高于一切票务展示态，不能被“现在预约”等动作文案盖住。
- 取消提醒不能洗掉已经存在的 `MISSED` 记录。
- 三项菜单按条件展示：删除这条恒有；标记结果读取 `canMark`；提醒开关读取 `canSetReminder`，且只显示当前可执行的开启或取消。
- `canSetReminder` 不是 `ticketState`；它由“需预约、有放票时刻、放票时刻未到”共同决定。

## 时间线与清单

- `timeline.preview` 是纯预览，不创建或改写行程。
- 只有 `cart.commit` 才创建/合并行程并创建提醒任务。
- 时间线顶部 `releaseState` 与按钮 `status` 是两套字段，禁止合并。
- 已开票项仍可加入清单，但必须固定不提醒；服务端下发 `remindLocked=true`。清单副行改为绿色「已放票」，点击禁用的提醒控件时提示「放票时间已过」。
- 清单是提交前暂存区，提交成功后清空。
- 清单只承载当前这次生成的时间线：`timeline.preview` 成功后调用 `cart.pruneScope`，移除暂存区中不属本次日期段或景点集合的草稿；同范围草稿继续跨退出/重启保留。
- 用户显式删掉账号里的最后一笔行程项后，无主暂存清单一并清空；账号仍有其他行程项时，暂存草稿继续保留。
- 清单按出行日分组；弱提醒、免预约、已开票的提醒控件行为不同，必须按服务端状态渲染。

## 授权与提交

- PAGE-008 是硬闸门：额度不足时主按钮禁用，用户必须主动补齐，不允许自动补齐，也不提供“仅加行程”旁路。微信一次性订阅每次用户点击最多增加 1 条同模板额度；“总是保持以上选择”只免弹窗，不改变单次授权上限，页面必须如实展示剩余缺口。
- 授权健康输出固定五态：`idle / ready / low / short / exhausted`，必须保留一次安全缓冲。
- 首页额度预警：`short / exhausted` 是真实缺口，立即下发；`low` 仅表示缺 1 次缓冲，仍限制在最近提醒进入 48 小时内。
- 景点页轻量入口可一次选择多个日期；首页「约其他日」只选择一个日期。两者确认后都按本次实际待建提醒数校验授权，并通过 `cart.quickCommit` 一次性提交本次选中项。
- 景点页多日期先走 `cart.planQuickDates`：服务端返回 `REMINDABLE / TRIP_ONLY / IN_TRIP`，旧版 pending 同景点日期可续用但不得显示成主流程清单重复。全部只能加入行程时不得自动提交，必须在统一浮层明确确认；部分可提醒时按实际可提醒数过授权和名额闸门。
- 快捷入口不得先写 `reminder_cart`：新建日期由 `cart.quickCommit` 直接在同一事务中创建行程项与任务；历史 pending 行只消费匹配的景点日期，其他暂存草稿保留。`cart.addDates` 仅保留兼容旧客户端，不再作为当前景点页调用入口。
- `confirmReminderAccess()` 的 `trip-only` 分支只用于景点详情直设提醒等未迁移的轻量入口；首页「约其他日」必须复用 `reminderFlow`。
- 景点卡片、景点详情、分享场景和首页「约其他日」使用一个标题为「设置提醒」的统一浮层，同时检查订阅授权和提醒名额；授权卡、三条说明与样式入口复用 PAGE-008。授权区固定显示「点击补授权次数」，每次只发起一次微信订阅，补足后由用户点击底部「开启行程放票提醒」继续；`membership.status.enforced=true` 且名额不足时，同一浮层展示名额公式和「支付并继续」入口，底部按钮置灰。名额支付到账后自动完成原提醒；若授权仍有缺口，则保留浮层，补齐后自动完成。不得逐次重新弹系统 ActionSheet，不得自动连发授权，也不得跳「提醒设置」页让用户重做。只有系统通知、订阅总开关或历史拒收需要设置时才打开设置引导。真身见 `REMINDER-RULE-009`。
- 设置提醒前判断的是**可用授权**：`subscribe.get.quota − pendingMessageCount`。未来 `WAITING` 任务尚未发送，但已经占用微信一次性订阅次数；只看 `quota` 会让新增提醒重复承诺同一笔授权，最终出现「未送达」。
- 授权页面展示同样必须区分「台账已授权」与「当前可用」；待发送提醒占用额度时写明占用数。授权拒绝、到账被占用或云端未同步时，页面内必须保留可见反馈，不能只弹 Toast，也不能仅凭微信回调成功宣称已补齐。
- 任一入口都不得静默提交，也不得在提醒未真正创建时提示“提醒已设置”。
- `cart.commit` 必须在建任务前按服务端台账二次校验订阅额度；余额不足返回 `1008`，不得先建行程或部分消费清单。页面刷新授权卡并保留日期、清单、提前量供重试。
- `tripItem.updateReminder` 开启提醒也必须执行同一服务端订阅额度校验；行程项开关前端在竞态失败后保留原状态并提示用户重新点击，不得在异步回调里脱离用户手势直接拉起订阅授权。
- 微信订阅消息按条授权：一次有效授权可发送一条提醒。
- 订阅模板按任务保存：新任务写当前模板，旧任务无 `templateId` 时继续走旧模板；额度核销、43101 清零、台账自愈和可用额度健康度都按任务实际模板处理。不同模板的待发送数不能互相占用额度，首页预警取最危险的一组。

## 会员、提醒名额与支付

- 用户侧统一使用「提醒名额」，不再使用「任务位」；会员定义为 30 天提醒名额扩容，不是抢票服务。
- 免费版上限 5。会员统一为 `¥8 / 30 天`，有效期内不限提醒名额；不自动续费。调价前订单仍按订单快照处理。
- 当前有效老会员自动获得不限权益，`memberExpiresAt` 不变。新购买或续费在原有效期末尾增加 30 天，已过期会员从支付成功时起算 30 天。
- 提醒加量包已停售。历史 `taskPackCount/taskPackSlots` 保留用于展示、对账和退款，不再参与新会员额度计算。
- 老用户历史保护池为 `max(5, 上线前当前未来 WAITING 提醒数)`，与免费/会员新增池独立。任务创建时处于 `off` 或 `test` 非白名单的进入保护池，`test` 白名单或 `all` 下创建的才计新增池；历史任务结束后不释放可继续新建的免费名额。
- 提醒名额只统计未来仍会发送的 `WAITING` 提醒任务；已触发、已过期、已关闭任务不长期占用新名额。
- 所有创建提醒任务的入口必须在服务端校验提醒名额；`cart.commit` 和 `tripItem.updateReminder` 不得绕过。超额时整体失败，不得先建行程或部分消费清单。
- 景点卡片、景点详情和分享场景收到 `cart.commit` 的 `1026` 时，必须先在同一「设置提醒」浮层展示服务端返回的额度公式、本次新建数和缺口，再由用户主动支付或进入会员页；不得在错误处理中自动 `navigateTo`。关闭说明时清理本次未提交的暂存清单，避免下次重选命中旧草稿。
- 会员到期不删除既有提醒。已有任务照常发送；会员到期后新增提醒按免费版 5 个名额校验。
- 微信后台自动广告无法按会员身份关闭；产品不得承诺“免广告”，除非平台明确提供人群排除能力。
- 支付成功唯一依据是服务端取得微信支付 `trade_state=SUCCESS`；`wx.requestPayment.success` 只代表客户端流程结束。
- 主订单状态固定 `PENDING / PAID / CLOSED`；退款生命周期独立存于 `refundStatus`，不得混入订单主状态。
- 支付后 24 小时内且支付后没有新增任何提醒，可申请未使用退款，由客服审核。提醒删除后仍算已使用。
- 未到账、重复支付和系统故障优先自动查单、补发或核验退款。每笔订单最多一次全额退款，V1 不做部分退款。
- 退款成功后只按本订单已确认发放的权益快照回收会员时长和权益，不影响其他订单，不删除用户已有提醒；权益发放失败时只记录退款结果，不得修改用户权益。
- iOS 虚拟支付订单由用户在 Apple App Store 购买记录发起退款，小程序内不重复受理退款申请。Apple 审核期间会员权益保持有效；Apple 拒绝退款时不回收权益，确认退款并推送结果后由服务端查单确认，再按本单快照回收。最终结果与到账时间以 Apple 为准。
- 会员购买总开关唯一真身为 `payment_config/membership_sales`，与会员限制模式完全独立。暂停只阻止新下单和待支付订单新发起支付；已打开的外部支付窗口可完成，支付回调、主动查单、权益发放、退款和售后必须继续。读取配置失败时新购买按暂停处理，但会员状态和订单读取不得失败。
- 会员限制模式唯一真身为 `payment_config/membership_enforcement`，`mode=off|test|all`。切换只影响之后新建任务的 `quotaPool`，已有任务不追溯重算；`all` 必须同时通过保护额度与权益账本迁移检查。`MEMBERSHIP_ENFORCEMENT_MODE` 只在配置缺失、非法或读取失败时兜底，不能与后台配置形成第二套真身。

## 景点规则数据

- `shortName` 只允许用于窄容器；行程卡、清单、详情和景点列表使用全名。
- `advanceDays` 表示提前几天放票，不表示“不可约”。
- `openDays` 非空时接管 `closedDays`，两者不叠加。
- `closedDaysNote` 只影响展示，不进入开放日判定。
- `specialNotice` 必须配 `specialNoticeUntil`；过期后不得继续下发。
- 未核验景点必须显示“尚未复核，以官方为准”，不得硬编码核验清单。
- 景点规则的任何值都必须先得到用户确认，禁止根据资料置信度推断。

## 景点分层

- C：免预约，可进行程和时间线，不创建提醒任务。
- S：需预约且困难度 ≥4，优先进入热门推荐。
- A：需预约且困难度 ≤3，用于混搭补足。
- `addable = 所有景点均可加入行程`；无固定放票时刻的需预约景点（如环球影城）也属于可加入项。
- `remindable = 需预约 && 有放票时刻`。
- 需预约但没有固定放票时刻的景点可加入行程和时间线，但不进入提醒流程、不可设提醒。
- `weak = 需预约 && difficultyScore ≤2 && strongReminder !== true`。
- `strongReminder=true` 用于把指定的低难度景点显式提升为强提醒；只改变文案与默认提醒策略，不改难度、放票规则或可约性。
- 强提醒默认可提醒项勾选，弱提醒默认不勾选；已开票与无固定放票时刻的项固定不提醒。
