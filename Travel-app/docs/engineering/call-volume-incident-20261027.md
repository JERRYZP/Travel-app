# 2026-10-27 调用量暴增复盘：第一性原理归因与优化方案

> 事件：开通流量主当天，访问从每天 20–30 人涨到半天 1500 人，云函数调用次数从每天约 1 万涨到半天约 59 万（本周期额度 20 万，一天烧掉近三个月的量）。
> 本文回答三件事：钱（额度）花在哪、为什么架构上必然这么花、怎么把它降回去。
> 配套事实见 `current-state.md` 的「2026-10-27 调用量降本」一节，本文不重复已完成的改动清单。

## 0. 结论先说

1. **今天不是"出了 bug"，是"单价太贵"被流量放大了。** 平常日 1 万次 ÷ 30 人 ≈ 每人 330 次；今天 59 万 ÷ 1500 人 ≈ 每人 390 次。单人成本前后同一个量级——流量涨 50 倍，账单就涨 50 倍，中间没有任何一层缓冲。
2. **贵的根因是一条底层设计选择：所有"看数据"的动作都走云函数调用。** 云函数调用是这套环境里最贵的运输方式（调用额度、冷启动、计算 CU、数据库读一次全记在账上），而项目里绝大多数读请求拿的是"一天改不了几次"的静态运营数据或"上次看过之后没变过"的私有数据。
3. **成本的驱动变量是"切屏次数"，不是"用户意图"。** 线上版本的首页是"每亮一次屏就重新问一遍云端"，而亮屏次数由微信的切换机制决定、用户和我们都控制不了——所以单用户成本没有上界。这是第一性原理层面最致命的一条。
4. **已提交未发版的客户端降本改动（30 秒复用窗口、景点缓存、清单去重）是当前最大的现成杠杆**，发版即可生效，不需要再写代码。
5. **有一个对不上的账**：按所有能找到的代码版本建模，单人一次会话只该产生 10–30 次调用，解释不了 330–390 次。缺口要么在"1500 人"这个分母的口径里，要么在线上包里有一段不在 git 里的代码。第 4 节给了 5 分钟能查完的两个数。

## 1. 账怎么记：云开发"调用次数"到底在数什么

把"调用次数"当成一种货币来理解：小程序每 `callFunction` 一次、定时器每触发一次云函数，就花掉一次额度，同时还会连带花掉：

- **计算 CU**（内存 × 运行时长）：本次事件里今天 3295 CU ÷ 59 万次 ≈ 每次 0.0056 CU，折合 256MB 内存下约 20–30 毫秒——说明今天的主力调用是"热实例上的轻调用"，不是冷启动重调用。平常日 717 CU ÷ 9.37 万 ≈ 每次 0.0076 CU，同一个profile。**即：暴增的不是某种异常调用，而是平常那种轻调用被放大了 50 倍。**
- **数据库读次数**：每次调用内部再记一笔（`current-state.md` 已记录读操作同步暴涨）。
- **并发与冷启动风险**：调用越密，冷启动和排队越多，失败率上升又会诱发客户端重试行为。

免费额度是 20 万次/月。按今天的单人成本（≈390 次/人），**这份额度只够约 510 个"今天这种用户"**——产品只要再小爆一次就必然超额。这就是"成本远大于收益"的结构原因：流量主收入按曝光线性涨，而我们的成本按"人数 × 每人切屏次数"线性涨，后者的系数比前者大一个量级。

## 2. 第一性原理归因：四层问题，从底层往上

### 层 1（运输层）：读多写少的数据，走了最贵的通道

景点与规则全表只有 26 条，一天改不了几次，却被 6 个页面通过 `spots.list` 云函数拉取。云函数调用对这类数据是错配：它适合"要算、要鉴权、要写库"的请求，不适合"把一份半天不变的 JSON 交给屏幕"。
**第一性原理表述：数据的变更频率决定它该走哪条通道。** 变更频率以"天"计的数据应该走静态文件 + CDN（云存储直连），变更频率以"秒"计且私有的数据才配走云函数。
现状是全部走云函数，于是每次页面露出都付一次"最贵通道"的钱。今天部署的"云函数内 60 秒整表缓存"省的是数据库读，**省不了调用次数本身**——调用次数是在门口记的账，进门之后哪怕什么都不干也记一次。

### 层 2（触发层）：成本挂钩"亮屏次数"，而不是"用户意图"

线上版本的首页 `onShow` 无条件 `loadHome()`：从聊天切回来、从别的页面返回、下拉回到前台，每一次都发一次 `home.bootstrap`。微信的 `onShow` 频率由用户的使用习惯决定（重度微信用户一天切回某个小程序几十次很常见），**这个变量既不受用户控制、也不受我们控制，还没有上界**。
于是单用户成本 = 切屏次数 × 每次全量聚合，而不是 = 用户做了几个动作。这是"每人几百次"在结构上的来源方向。
已提交未发版的 30 秒复用窗口是对的方向，但只是"止血带"：窗口外的第 31 秒照样全量重拉。真正的解法是让刷新频率挂钩"数据可能变化的紧迫度"（见 5 节 P1-⑥）。

### 层 3（阻尼层）：整条链路没有任何缓冲、限流、熔断、告警

缓存（发版后才有）、限流（没有）、熔断（没有）、额度告警（没有）、单人预算（没有）。
**第一性原理表述：一个没有阻尼的系统，会把输入端的任何波动原样传递到账单端。** 今天流量 ×50，成本 ×50，中间零衰减——这不是运气不好，是架构上就没有可以衰减的位置。
对照：提醒发送链路有台账自愈哲学（失败留痕、不静默），但成本链路完全没有对应的"失败留痕"——额度烧到 59 万才发现，本身就是监控缺失的症状。

### 层 4（治理层）：线上跑的是哪份代码，答不上来

`95ad0ce` 的提交说明写得很清楚："线上已发布的版本此前没有任何版本记录"。事故当天线上客户端 = 未含本日降本改动的旧包，且旧包与 git 任何提交都不严格对应。
后果在今天就兑现了：**复盘时无法拿到"线上真正在跑的那份代码"来做归因**，只能靠所有可恢复版本建模 + 推断。版本治理缺失把一次成本事故升级成了一次"取证困难"的事故。

### 附：固定成本（小但永远不为零）

`notifier` 定时器每分钟触发一次（1440 次/天），其中 `scanAndSend` / `sweepMissed` 每分钟各扫一次库（约 2880 次索引命中/天）。占今天总量的 0.2%，不是本次事件的原因，但它是"哪怕没有一个用户也每天必花"的钱，且随额度紧张会变得刺眼（见 P1-⑦）。

## 3. 单用户调用预算模型（线上旧版 vs 发版后 vs 目标）

按动作拆解一次会话的调用次数（云函数调用口径）：

| 用户类型 | 线上旧版（今天跑的版本） | 发版后（已提交待发布） | 目标（P1 完成后） |
|---|---|---|---|
| 看一眼就走（分享落地） | 2–4（bootstrap + spots.list + 可能的 detail） | 1–3 | 0–1（静态数据不走调用） |
| 正常浏览（翻景点、搜索、开详情） | 8–15（每次回首页重拉 + 每页各拉一次景点表） | 5–9 | 2–4 |
| 完整转化（建行程 + 设提醒全流程） | 25–40（add-trip 重复 cart.list、setup 再拉清单与额度、每次返回首页重拉） | 18–28 | 8–12 |

要点：**即使发版后，一个转化用户仍要近 20–30 次调用**，因为"每次写操作后静默重拉整面状态墙"的模式没变（写 1 次 = 写调用 + 全量读调用）。目标态靠"静态数据下放到云存储 + 刷新频率挂钩紧迫度 + 写后局部更新"再砍一半以上。

## 4. 对不上的账：59 万 ÷ 1500 = 390，模型只给到 10–40

这是本文最重要的诚实声明：**按所有能恢复的代码版本（线上旧版行为 + 旧版页面调用点）建模，单会话 10–40 次；要凑到 390 次/人，需要每人一次会话里亮屏/翻页几十次以上，或线上包含有一段不在 git 里的循环代码。** 两个候选解释，用下面两个数 5 分钟内可以裁决：

1. **微信后台 → 统计 → 今日"打开次数"(PV) 与"访问人数"(UV)。**
   - 若 PV 是几万量级（人均打开几十次，分享风暴里反复点开有可能）：分母口径问题成立，"每人 390 次"其实是"每次打开 10 次 × 人均打开 39 次"，层 2 的 onShow 重拉就是主放大器，发版 + 自适应窗口即可解决。
   - 若 PV 只有几千：说明线上包里有 git 之外的循环代码。**去微信后台"版本管理"把线上代码包下载回来反解 diff**——这是唯一能取回线上真身的途径，也顺便补上层 4 的治理欠账。
2. **云开发控制台 → 云函数 → 监控/日志：今天各函数的调用次数分布 + 抽样日志里的 action 与 openid 分布。**
   - 某个函数独占几十万 → 盯该函数的触发链（客户端调用点或定时器配置）。
   - openid 高度集中在少数账号 → 个别客户端循环或外部刷量；分散在全部用户 → 全体行为模式问题。
   - 顺带确认 `notifier` 今天是否仍是 1440 次（排除定时器配置漂移）。

在裁决之前，不要把"390 次/人"写进任何对外结论；本文其余结论不依赖这个数字成立。

## 5. 优化方案（分级，按"先止血、再降本、后改结构"）

### P0 — 今天做，止住出血

1. **发版客户端。** `95ad0ce` 里的三项客户端降本（首页 30 秒复用窗口、`spots-cache` 10 分钟跨页缓存、add-trip 去重）已提交未发版（`current-state.md` 部署表已标注）。这是零开发量的最大杠杆。发版需要用户当场确认。
2. **查第 4 节的两个数**，裁决归因缺口；若发现线上包有 git 外代码，取回线上包 diff 后再决定是否需要热修。
3. **额度告警**：云控制台对"调用次数"设阈值告警（建议 50% 额度即报）。今天如果有告警，上午就能发现而不是半天后。
4. **（可选熔断，需用户拍板）服务端单人限流**：`home.bootstrap` 对同一 openid 每小时超过 N 次（建议 60）时直接返回上一次的成功形状或空成功，不再查库。作用是"哪怕某个客户端出现循环，也烧不穿全量额度"——把层 3 缺失的阻尼先补一个最便宜的。注意：这会改变极端场景下的数据时效，需产品确认接受。

### P1 — 本周做，把单价打下来

5. **景点/规则静态化下放云存储 + CDN。** 由 seed/导出脚本把 `data/spots.json` + `data/rules.json` 发布到云存储固定路径（如 `static/v0.3/data/spots.json`），客户端用 `wx.request` 直连（带 10 分钟缓存与失败降级包内切片）。`spots` 云函数退出热路径，只保留搜索/纠错等真需要算的 action。预期砍掉 30–40% 调用次数，且这部分成本从此与人数解耦（CDN 流量单价远低于调用）。数据真身仍是 `data/*.json`，发布走脚本钉住，不制造第二套真相。
6. **首页刷新频率挂钩紧迫度，替代固定 30 秒窗口。** 规则表能算出"今天最近一场放票离现在多远"：临近放票窗口（如 ±2 小时）用 30 秒；平时用 5 分钟；用户主动下拉/写操作后照常即时刷新。成本 ∝ 数据可能变化的概率，而不是 ∝ 亮屏次数——这是层 2 的根治。
7. **notifier 扫描改放票窗口自适应。** `scanAndSend` / `sweepMissed` 在"当天无任何放票时刻 ±30 分钟"的时段降为每 5 分钟一次，窗口内恢复每分钟。固定成本降约 80%，且不影响提醒时效（窗口内仍是每分钟）。需评估 `sweepMissed` 降频对"待提醒"卡单的影响面后再动。
8. **给"单会话调用预算"加回归测试。** 在 `test/` 增加会话模拟：脚本化跑一遍"落地→浏览→转化"标准会话，断言云函数调用次数 ≤ 预算值（建议先定 30，P1 完成后收紧到 15）。以后任何页面改动想偷偷加调用，测试先红。

### P2 — 结构性改造，按排期进

9. **读模型写时聚合。** 把首页状态墙需要的派生字段（progress、ticketState、nextReminderAt）在写操作落库时同步写进每用户一张摘要文档，`home.bootstrap` 从"多集合联查"变成"读 1 张摘要 + 增量修正"。单次调用的 CU 与数据库读随用户数据量不再上涨（顺带解决 `users` 集合平方级成本问题）。
10. **单位经济台账。** 每月一行：DAU、人均调用次数、人均云成本（按控制台单价）、人均流量主收入。让"成本远大于收益"从体感变成一张表，流量主的去留、免费额度的水位、要不要为重度用户做功能分级，都看这张表决策。
11. **版本治理补欠账。** 每次发版必须：git 打 tag（如 `release/2026-10-27`）+ 在 `current-state.md` 记录"线上版本号 = 该 tag"。杜绝"线上跑的是哪份代码答不上来"再次发生。

## 6. 预期效果

- 发版（P0-1）：单会话调用约降 30–50%（复用窗口 + 景点缓存 + 去重）。
- P1 全落地：单用户日调用从"几百次量级"压到 **≤15 次/会话**；同样 1500 人/天，日调用从 59 万回落到 **2–3 万**，重新落回免费额度安全线内（20 万/月 ≈ 允许每天 6–7 千转化级会话或数万轻会话）。
- 成本与流量的关系从"线性穿透"变成"分段阻尼"：静态数据与人数解耦、刷新与紧迫度挂钩、单点循环有熔断、额度有告警。

### 8.2 归因修正：放大器是"每页面 PV 约 20 次调用"，且大概率集中在 spots

- 第 4 节的"PV 分母"候选被裁决掉一半：页面 PV 确实是万级（2.86 万），但打开次数只有 4,302、浏览深度正常——**放大器不在"打开太频繁"，而在"每个页面视图太贵"**（20.6 次/PV，模型值 1–3 次/PV）。
- CU 反推给出函数级拆分假设：reminder 24h 资源 2761 GBs ÷（0.15 s × 0.25 GB）≈ **7–8 万次**；今日总 CU 3295 减去 reminder 部分后，剩余资源对应约 **50 万次平均 10–20 ms 的轻调用**——与"旧客户端无 spots 缓存、六个页面每次 onShow 各拉一次 `spots.list`（旧包内可能还有更多触发点）"的形状吻合：轻、快、随页面露出线性发生。
- 待确认（一张截图即可）：云函数监控下拉切到 `spots`，读其 24h 调用次数 / 资源总计 / 平均运行时间。若调用次数 ≈50 万、平均 ms 为十几毫秒，假设成立。
- 该假设若成立，则今日已生效的两项改动（客户端 `spots-cache` 已发版 + 云端 60 秒整表缓存已部署）**正好打在出血点上**，明日比率应断崖下降。

### 8.3 openid 集中度：当前日志体系看不了，且大概率不需要看

- 事实：`reminder` 成功路径不打日志（仅失败 `console.error` 与 `[bootstrap-timing]`），平台日志不含 openid ⇒ **现有日志无法按 openid 分组**，这不是操作问题而是日志体系缺口。
- 但 8.1 的三条排除（波形、浏览深度、零错误）已使"少数 openid 循环"成为低概率假设；优先级让位于 8.2 的函数级拆分确认。
- 若日后仍需要 openid 级归因：唯一干净做法是在调用 wrapper 或云函数入口加一行 `openid + action` 日志后发版观察（属代码改动，需单独授权）；或使用云开发"日志检索"对 `[bootstrap-timing]` 计数得到 bootstrap 占比（无代码改动，今天即可做）。

|---|---|---|---|
| 调用次数 ÷ 页面 PV | 20.6 | ≤3 | 每页成本回到模型值 |
| 调用次数 ÷ 打开次数 | 137 | ≤15 | 单会话预算回到设计值 |
| `spots` 函数日调用 | 待确认（假设≈50 万） | <5 千 | spots-cache + 云端缓存生效 |

连续两天达标即关闭本事件；任一比率反弹回旧量级，按 8.2 顺序重新取证（届时线上包已有 git tag 可对，不会再出现"线上真身不可知"）。

### 8.5 实测第三轮：spots 裁决与新缺口（16:10 截图）

**spots 风暴假设被证伪。** spots 函数近 24h 资源 702.9 GBs、平均运行 50–150 ms，按默认 256MB 内存折算执行次数 ≈ 702.9 ÷ (0.25 × 0.07) ≈ **4 万次**，不是 50 万。reminder 同法折算 ≈ 85 万次…更正：≈ 8.5 万次（2761 ÷ (0.25 × 0.13)）。加 notifier 1,440 与其余近零函数，**六函数执行次数合计 ≈ 13 万**，与计费口径"调用次数 59 万"相差约 46 万。

客户端侧已排除隐藏调用点：全仓库 `wx.cloud` 仅三处（wrapper 的 callFunction、profile-edit 的 uploadFile、app.js 的 init），旧版（44e702c）同样无直连数据库代码。

于是出现两种互斥解释，用一张截图裁决：

- **解释甲：执行次数确实≈59 万，"运行时间"图不是每次执行的平均。** 若真实平均约 20–30 ms，则 59 万 × 0.25 GB × 0.022 s ≈ 3,245 GBs，与总 CU 3,295 精确吻合——即运行时间图展示的是慢调用样本或含排队口径，CU 才是真相。此时 reminder 约 25–30 万次、spots 约 10–15 万次，归因回到"旧客户端每次亮屏/每页重拉"，明日发版后比率测试仍是收队证据。
- **解释乙：六函数执行合计≈13 万，计费"调用次数"≠函数执行。** 则资源页的"调用次数"把数据库读、云 API 等一并计入（数据概览里"数据库调用次数"曲线峰值 1.2 万/桶与此相容）。此时主降本战场是**数据库读次数**，P1-5 静态化下放的优先级升为最高。

**裁决动作（均无代码改动）**：云函数监控页 reminder 与 spots 各自**向下滚动**，读"调用次数"卡的近 24h 总计（截图被截在"常驻云函数个数"处，该卡应在其上下）；再点资源页"调用次数"旁的 ⓘ 读计费定义。顺带截 notifier 的调用次数总计（若≈8.6 万则定时器被平台按秒解析，属独立故障）。

### 8.6 不受裁决影响的既结论

无论甲乙：① 流量为真人真浏览、非刷量、非重试风暴（8.1 三条排除不变）；② 旧客户端"每页 20.6 次计费调用"的成本形状不变，已发版的三项客户端降本与已部署的云端缓存都打在该形状上；③ P0/P1 方案清单不变，仅解释乙成立时 P1-5 提前。明日 00:00 起的三比率观察（8.4）仍是事件关闭条件。

### 8.7 实测第四轮：计费定义裁决，全账对齐（16:30 截图）

资源页 ⓘ 给出"调用次数"的官方定义，**解释乙成立**：该指标是复合口径，包含——

1. 云存储上传/下载/临时链接等 API 调用；
2. CDN 回源产生的调用次数；
3. **基于数据模型的新增、删除、修改、查询等 API 调用（即数据库读写）**；
4. 云函数调用次数；
5. 用户登录、退出、刷新 token 等 API 调用；
6. AI 和 Agent 相关 API 调用。

据此全账对齐：

| 组成 | 估算 | 依据 |
|---|---|---|
| 云函数执行 | ≈13 万 | 三函数 GBs ÷ (0.25GB × 图表平均 ms)，与运行时间图 100–200ms 自洽 |
| 数据库文档读 | ≈45 万 | 59 万 − 13 万 − 杂项；与数据概览"数据库调用次数"峰值 1.2 万/桶同量级 |
| 存储/CDN/登录杂项 | ≈1 万 | 打开 4,302 × 登录/token 约 2 次 + 存储上传个位数 |
| CU 悖论消解 | 3,295 CU ÷ 13 万执行 ≈ 0.025 GBs = 100ms@256MB | 与运行时间图精确吻合；数据库读不耗 CU |

**"每页面 20.6 次"的真身是数据库文档读，不是函数执行。** 乘数终于找到：`spots.list` 每次执行读 26 条景点 + 26 条规则 = **52 次文档读**，旧客户端六个页面每次露出各发一次；`home.bootstrap` 每次执行读 10–30 次文档（旧版含 N+1 与全历史扫描）。加权后每页面 PV ≈ 20.6、每人 ≈ 313，与实测完全吻合；平常日 30 人 × 约 300 次 = 1 万/日 likewise。**第 3 节的预算表应以"计费调用（含文档读）"口径重读：旧版转化用户 300–400 次计费调用，其中八成是文档读。**

notifier 裁决：24h 73.42 GBs ≈ 2,900 次执行，分钟级 tick + 放票时刻发送峰，**无按秒误解析**。云函数外网出流量 24h 仅 80.41 KB，**排除外部扫描流量**。

**对方案的影响**：

- P1-5（景点/规则静态化下放云存储+CDN）升为**最高优先**：它一次消掉"每次 52 读"的最大读源，且把这部分成本从"调用次数"口径移到 CDN 流量口径（26 景点 JSON 约百 KB 级，按打开×无缓存页估算约 1 GB/日，10GB 额度内）。
- 已发版的客户端 spots-cache 同时砍函数执行与 52 读/次，是今日已生效的最大单项收益；云端 60 秒整表缓存砍缓存未命中时的 52 读。
- 下一战场是 bootstrap 的每次读文档数：N+1 与全历史扫描已修，剩余靠 P2-9 摘要文档。
- 8.4 观察口径不变（同一计费口径），期望值修正：调用÷页面 ≤6、调用÷打开 ≤40（新客户端下 bootstrap 读仍计入）。

**流程教训**：指标名"调用次数"直觉上像"函数调用次数"，但计费口径的唯一权威是计费页 ⓘ 定义。此前两轮归因偏差（spots 风暴假设、CU 悖论）都源于按名字猜口径。今后任何成本分析第一步先读计费定义。
