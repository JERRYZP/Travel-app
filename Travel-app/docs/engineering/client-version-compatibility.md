# 新旧客户端交叉期兼容标准

> 适用范围：API 响应、价格与权益、默认值、字段语义、数据结构和付费商品发生不兼容变化时。
>
> 核心结论：不要等旧客户端“自然消失”。由新客户端声明能力，服务端默认继续返回旧契约，再用白名单和运行期开关扩大范围。即使切到 `all`，`all` 也只表示“所有声明了该能力的新客户端”，不包含未声明的旧客户端。

## 1. 要解决的问题

小程序、App 和 Web 的发布链路彼此独立。提交审核、灰度发布、应用商店缓存、用户长期不更新，会造成以下状态同时存在：

- 旧客户端访问新服务端。
- 新客户端访问尚未升级的服务端。
- 审核版本、体验版本、正式版本和本地开发版并存。
- 同一用户在不同设备或不同缓存版本上看到不同契约。

因此不能用“发版后等几天”判断旧版本已经消失，也不能假设旧客户端会正确忽略新字段。兼容必须由协议和服务端路由保证。

## 2. 标准模型

一次兼容升级同时存在三套概念，不能混为一谈：

| 概念 | 作用 | 示例 |
|---|---|---|
| 旧契约 `legacy contract` | 保证已安装旧客户端继续可用 | `legacy-v2`、¥3、15 个提醒名额 |
| 新契约 `new contract` | 新客户端能力和权益的完整定义 | `unlimited-v3`、¥6、30 天不限提醒名额 |
| 能力声明 `capability token` | 客户端告诉服务端“我能正确处理哪套契约” | `membershipCapabilities: ['unlimited-v3']` |

能力声明只负责契约路由，不等于权限、身份或支付资格。真正能否开通、价格多少、权益多久，仍由服务端白名单、订单快照和业务规则决定。

## 3. 必须遵守的设计原则

1. 旧契约是默认值。字段缺失、格式错误、能力未知时，一律回退旧契约。
2. 能力使用稳定、可读、可版本化的标识，不使用客户端版本号或模糊布尔值。禁止用 `newPlan: true` 作为长期协议。
3. 新旧响应隔离。不能让旧客户端看到新价格、新权益、新的有限额度占位值或只对新客户端有意义的字段。
4. 新增字段优先，旧字段不要改语义。必须保留的兼容字段要明确注释其用途和退役条件。
5. 服务端是价格和权益的唯一权威。客户端不能传价格、有效期、赠送额度或商品规格。
6. `all` 只对声明能力的新客户端生效。未声明能力的旧客户端永久走旧契约，直到旧契约正式退役。
7. 灰度至少保留两个独立维度：客户端能力是否命中，以及用户是否在测试白名单或运行期灰度范围内。
8. 付费订单必须保存下单时的规格快照，包括金额、天数、权益、商品版本和是否不限量。后续规则变化不得回写下单快照。
9. 旧待支付订单、已支付订单、退款和售后继续按订单快照处理，不因新商品上线而失效。
10. 客户端升级、后端部署、配置切换、体验版上传、提审和正式发布是六个独立状态，不能互相替代。

## 4. 服务端路由规则

所有需要兼容升级的入口共用同一判断顺序：

```text
请求未声明能力
  -> 返回旧契约

请求声明了未知或不支持的能力
  -> 返回旧契约

声明能力 + 灰度模式 off
  -> 返回旧契约

声明能力 + 灰度模式 test + 用户不在白名单
  -> 返回旧契约

声明能力 + 灰度模式 test + 用户在白名单
  -> 返回新契约

声明能力 + 灰度模式 all
  -> 返回新契约
```

建议服务端统一封装能力判断，禁止每个接口各写一套判断：

```js
const newContract = hasCapability(request, 'capability-name')
  && rolloutAllows(request.userId, rolloutMode);
return newContract ? buildNewContract() : buildLegacyContract();
```

同一轮升级中的所有相关接口必须使用同一判断函数、同一能力标识和同一灰度配置，避免会员页是新方案、下单接口却仍是旧方案。

## 5. 兼容响应约定

新契约应显式返回足够的版本信息，至少包括：

- `contractVersion` 或业务版本字段，例如 `planVersion`。
- 新权益的明确语义，例如 `unlimitedReminders: true`。
- 可选的兼容投影字段，以及“新客户端不得使用”的注释。

旧契约不得返回新契约的兼容占位值。以会员为例，`taskLimit=10000` 只能存在于已完成新契约路由的响应中，不能下发给旧客户端，也不能被新客户端当成业务上限展示。

兼容字段必须回答三个问题：

1. 谁会读取它。
2. 它是否参与业务判断。
3. 它何时可以删除。

## 6. 订单与权益快照

价格或权益发生变化时，订单至少保存以下信息：

| 字段 | 用途 |
|---|---|
| `packageId` | 稳定商品标识 |
| `productType` | 会员、加量包等商品类型 |
| `amountFen` | 下单时金额，单位为分 |
| `memberDays` | 下单时的有效天数 |
| `addedSlots` | 历史有限额度商品的名额增量 |
| `unlimitedReminders` | 是否为不限提醒权益 |
| `specVersion` | 商品规格版本 |
| `entitlementGrant` | 发放、回收和应用结果 |

读取订单、发起支付、退款和售后时只认订单快照，不按当前价格重新解释历史订单。新规则上线前的旧待支付订单继续支付和发放；只禁止创建已经停售的新商品订单。

## 7. 标准发布顺序

1. 定义旧契约、新契约、能力标识和完整响应矩阵。
2. 先部署兼容层和读取能力，不创建新商品、不切换新默认值。
3. 创建灰度配置，保持 `off` 或 `test`，把验收账号加入白名单。
4. 使用旧客户端、新客户端和白名单账号完成服务端矩阵验收。
5. 生成新客户端预览或体验版，只做白名单真机验收。
6. 新客户端送审期间继续保持 `test`，不要提前切 `all`。
7. 正式发布后，先观察旧契约占比、新契约错误率和支付结果。
8. 明确授权后把运行期开关从 `test` 切到 `all`。`all` 仍然只覆盖声明能力的新客户端。
9. 观察稳定后，再决定是否逐步退役旧契约。退役必须基于数据和明确决策，不使用固定天数。

涉及支付和会员时，通常先部署能兼容新旧订单快照的支付链路，再部署生成新订单的接口，最后发布新客户端。具体部署顺序以当轮文档和用户授权为准。

## 8. 标准验收矩阵

每次兼容升级至少验证以下组合：

| 客户端 | 灰度范围 | 期望结果 |
|---|---|---|
| 旧客户端，不声明能力 | `off` | 旧契约 |
| 旧客户端，不声明能力 | `test` 白名单 | 旧契约 |
| 旧客户端，不声明能力 | `all` | 旧契约 |
| 新客户端，声明能力 | `off` | 旧契约 |
| 新客户端，声明能力 | `test` 非白名单 | 旧契约 |
| 新客户端，声明能力 | `test` 白名单 | 新契约 |
| 新客户端，声明能力 | `all` | 新契约 |
| 未知能力或畸形能力 | 任意模式 | 旧契约 |

同时验证：

- 新客户端可以看到新价格、新权益和新文案。
- 旧客户端不会看到新价格、新权益或新兼容占位值。
- 新能力白名单用户可以创建新订单，非白名单仍创建旧订单。
- 旧待支付订单仍可支付和发放。
- 新订单退款只回收本订单权益，不影响历史订单和加量包。
- 新公告、新横幅、新入口同样受能力门禁约束。
- 返回结构和错误码在旧契约下保持不变。

## 9. 回滚原则

优先回滚运行期配置，不紧急回滚代码：

1. 把灰度开关从 `all` 切回 `test`，或从 `test` 切到 `off`。
2. 暂停新购买，保留已支付订单、查单、退款和售后。
3. 若已经产生新契约订单，继续按订单快照履约，不能按旧价格重算。
4. 只有协议实现本身有安全或数据破坏风险时，才回滚云函数代码。

回滚后必须再次验证旧客户端仍走旧契约，新客户端不再获得未授权的新权益。

## 10. 监控与退役条件

上线后持续观察：

- 按能力声明、契约版本、灰度模式和用户群体统计请求量。
- 新契约是否出现在白名单或 `all` 之外。
- 创建订单的金额、规格版本和权益快照是否一致。
- 支付失败、规格变化关闭订单、退款回收失败和客服工单。
- 旧契约占比是否持续下降，但不能把下降当成退役的唯一条件。

旧契约退役前至少满足：

- 新契约已稳定运行，且关键异常为零或可解释。
- 旧客户端占比达到明确业务阈值。
- 历史订单和售后的兼容读取路径已确认保留。
- 产品、工程和客服对退役影响有明确确认。
- 退役方案和回滚窗口已单独授权。

## 12. 反面清单

- 直接修改旧字段的默认值，再期待旧客户端自动适配。
- 把新价格或新权益先全量返回，再等待客户端发版。
- 用 `taskLimit=10000` 之类的有限数字假装“无限”，并让旧客户端读取。
- 用客户端版本号、审核时间或“旧包应该没了”判断兼容性。
- 让客户端提交价格、有效期或权益规格。
- 让新订单读取当前商品规则，而不是下单快照。
- 只限制页面展示，却没有限制下单、支付、额度校验和公告接口。
- 把 `all` 理解成“所有已安装客户端”，而不是“所有声明能力的新客户端”。

## 13. 当前会员升级案例

本轮会员升级可以作为标准案例：

| 维度 | 旧契约 | 现有契约 | 两档候选 |
|---|---|---|---|
| 能力声明 | 不声明 | `unlimited-v3` | `unlimited-v3 + two-tier-v5` |
| 方案版本 | `legacy-v2` | `unlimited-v3` | `two-tier-v5` |
| 价格 | ¥3 | ¥6 | ¥3 / ¥4.9 / 升级 ¥1.9 |
| 有效期 | 30 天 | 30 天 | 30 天；升级不延期 |
| 提醒额度 | 15 个，可购买加量包 | 有效期内不限 | 10 个或不限 |
| 商品 | `member`、`task_pack_5` | 仅 `member` | `member_quota_10`、`member_unlimited`、`member_unlimited_upgrade` |

关键实现约束：

- 新客户端在 `reminder` 请求中声明 `membershipCapabilities: ['unlimited-v3', 'two-tier-v5']`。
- 服务端先检查 `two-tier-v5` 与 `MEMBERSHIP_TEST_OPENIDS`；未命中时再按现有 `unlimited-v3` 路由；最后回退 `legacy-v2`。
- `two-tier-v5` 的定价灰度不再依赖当前生产额度模式 `all`，避免为了测试价格改动所有用户的额度限制。
- 旧客户端永远返回旧套餐、旧价格和旧额度，即使模式为 `all`。
- `unlimited-v3` 有效会员继续返回兼容字段 `taskLimit/taskRemaining/memberTaskSlots=10000`；`two-tier-v5` 不限会员返回 `taskLimit/taskRemaining=null`，3 元档返回真实 `taskLimit=10`。
- 会员升级横幅、公告接口和所有相关 bootstrap 接口都消费同一能力判断。
- 历史订单、旧加量包、退款和售后继续按订单快照处理。

这套模式不只适用于会员。以后遇到接口字段迁移、默认值切换、数据结构升级、付费商品替换或新权益灰度，都可以复用同一套能力门禁和发布矩阵。
