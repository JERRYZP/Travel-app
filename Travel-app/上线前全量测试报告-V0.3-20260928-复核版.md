## 三、确定性证据

### 3.1 主包体积超限（B1）—— 本次最重要发现

| 状态 | 主包体积 | 能否上传 |
|---|---|---|
| **HEAD 已提交版** | **2370.0 KB** | ❌ 超限 322 KB |
| 工作区当前 | 1986.5 KB | ⚠️ 可传，仅余 61.5 KB |

**复现方式**（把项目自己的检查脚本指向 HEAD 导出版）：

```bash
git archive HEAD Travel-app/miniprogram | tar -x
python3 scripts/check-miniprogram.py
# ✗ miniprogram 主包体积 2370.0KB 超过 2048KB；请压缩图片或拆分分包
```

体积构成：`images/` 占 **1663.9 KB（72.7%）**，纯源码合计 2286.9 KB，加 `miniprogram_npm` 构建产物 83 KB。

**关键点**：救命的 384 KB 来自**一批尚未提交的图片压缩**（`banner_bg` 94→68 KB、`beijing.png` 68→45 KB、`style-2.png` 282 KB 换成 108 KB 的 jpg、`style-1/3` 同步压缩）。**这些改动一旦丢失或被覆盖，项目立刻回到无法上传的状态。**

**根本问题**：工程无 CI、无 pre-commit hook，`MAX_PACKAGE_BYTES` 校验只在手动跑 `npm run check` 时生效；而 `miniprogram_npm/` 在 `.gitignore` 里，任何在干净 checkout 上跑的检查都量不到真实上传体积。且项目**未配置分包**，61.5 KB 余量挡不住后续任何一次加图。

### 3.2 测试套件的真实强度

全套 **6.5 秒**跑完 —— 这个数字本身就说明里面没有异步、竞态、超时路径。

按断言方式分类（扫描全部 25 套）：

| 类型 | 套数 | 行数 | 评价 |
|---|---|---|---|
| 真行为测试（stub 加载真实页面/云函数、`await` 驱动） | **23** | ~5062 | 扎实 |
| 源码正则匹配（`eq(/…/.test(WXML), true)`） | **2** | 1252 | 仅变更探测器 |

两个源码正则套件是 `home-emptystate`（940 行 / 159 处）和 `v03-main-flow`（312 行 / 81 处）。

**问题不在于正则本身，而在于断言抄的是实现里的数值**：

```js
eq(/\.quota-line\s*\{[^}]*margin-top:\s*-24rpx/.test(SETUP_WXSS), true, '本次提醒文案上移 12px');
eq(/\.sample-item\s*\{[^}]*width:\s*468rpx/.test(SETUP_WXSS), true, '提醒样式示例整体缩至原来的 90%');
```

连「上移 12px」都是从代码里的 `-24rpx` 反推的。**改代码，断言跟着改，永远绿。**

**公允地说**：`v03-main-flow` §5 是真测试——用 stub 加载真实 `setup.js`、模拟额度不足、断言 `apiCalls.commits.length === 0`（「额度不足绝不偷自动授权」）。这正是**不该** mock 的地方，写对了。`trip-wall-contract` 也诚实，自己标注「只锁定枚举名，不验证业务逻辑」。

**但口径要说准**：行为层覆盖扎实，**视觉/间距层（129 条纯源码正则断言）实际零有效覆盖**。像素回归必须靠真机截图，测试替代不了。

### 3.3 `app.js:20` 基础库兼容性（已查证）

```js
const sysInfo = wx.getWindowInfo();   // 基础库 2.20.1+
```

全项目 6 处 `getWindowInfo`，**只有 `app.js:20` 没写兜底**（其余 5 处都是 `wx.getWindowInfo ? … : wx.getSystemInfoSync()`）。

关于 `libVersion: "3.17.1"`：**它只控制开发者工具的调试基础库，不代表线上用户**。官方文档原文：

> 小程序的功能不断的增加，但是旧版本的微信客户端并不支持新功能，所以在使用这些新能力的时候需要做兼容。

线上用户的基础库版本由**用户微信客户端**决定；开发者只能在小程序管理后台设「基础库最低版本」（`设置 - 基本设置 - 基础库最低版本设置`）兜底，**低于该版本的用户直接打不开小程序**。

## 四、主流程功能缺陷（B2）

三条均已逐行核对，非推测。

### 4.1 提醒未设上，却提示「行程已添加，提醒已设置」【P1】

- **位置**：`miniprogram/pages/setup/setup.js:207-214`，配合 `cloudfunctions/reminder/lib/task.js:492-495`
- **触发**：清单加入后、提交前跨过放票时刻（例：19:55 加清单，20:05 提交）。服务端因此不建任务。
- **机制**：服务端算的是
  ```js
  const noReminder      = cartItems.length - reminderItems.length;   // ⊇ 过期项
  const expiredReminder = wantedReminderItems.length - reminderItems.length;
  ```
  过期项**同时**计入 `noReminder` 和 `expiredReminder`。而前端写成：
  ```js
  res.createdTasks > 0
    ? (res.noReminder > 0 ? '行程已添加，提醒已设置' : '提醒已设置，放票前见')
    : '行程已添加，未设置提醒'
  ```
  → 用户看到「提醒已设置」，实际少设了。
- **连带**：服务端专门为这种情况生成了文案「已加入行程 · N 项已过放票时间，提醒无法设置」，但**全站没有出口**——唯一读 `res.toast` 的是 `add-trip.js:670`，而那段代码不可达（见 4.2）。
- **违反自定规则**：`docs/engineering/domain-rules.md` 要求不得在提醒未真正创建时提示「提醒已设置」。

### 4.2 `add-trip` 的提交收尾逻辑是死代码，且责任方悬空【P1】

- **位置**：`miniprogram/pages/add-trip/add-trip.js:667`、`miniprogram/pages/setup/setup.js:219-221`、`:226`
- **事实**：
  - 有提醒项时 `onCartSubmit` 走 `navigateTo('/pages/setup/setup')`（`:653`），**不提交**，`afterCommit` 不执行；
  - `setup.js:221` 检测到 add-trip 在栈里就**不写** `tripId`，注释明写 *「add-trip 拿到返回值后会自己写」*；
  - 但 `setup.js:226` 又 `navigateBack` 退回首页，**add-trip 被 pop，永远拿不到那个返回值**。
- **实际影响**：`globalData.currentTripId` 不会被写。但**全项目没有任何地方读它**（只有 `app.js:11` 初始化和两处写入）。所以**用户无感**。
- **真正的问题**：`setup.js:219-221` 的注释描述了一个不存在的机制。代码只是**碰巧**无害，因为那个全局字段是死的。谁将来启用它，就会踩一个没有守卫的坑。
- **附带**：`add-trip.js:667` 引用了未导入的 `notify`（文件只 import 了 `api/util/mock`）。因短路 `createdTasks > 0 &&` 而不触发——**一旦 4.2 的调用链被修好，这里立刻抛 `ReferenceError`**。这两条要一起修。

### 4.3 挽回动线同样谎报「提醒已设置」【P1】

- **位置**：`miniprogram/pages/home/home.js:596-598`
- **触发**：「约其他日」选一个放票时刻已过的日期。`date-picker-sheet` 的 `minDate` 只限制「今天」，不管放票时刻；`cart.add`（`lib/cart.js:127-130`）内部会把 `remindOn` 落成 `false` → `createdTasks = 0`。
- **后果**：非 trip-only 分支**无条件**写「已加入 X行程，提醒已设置」，一个提醒都没建。
- **讽刺之处**：该函数上方 557-563 行的注释，描述的正是这个风险（*「用户换了个日期、行程项建好了、提醒却永远送不到——症状与未送达的静默失败一模一样」*）。**防线写在了注释里，没写进代码。**

### 4.4 时间线滚动联动无法回退到首日【P2】

- **位置**：`miniprogram/pages/add-trip/add-trip.js:210-221`
- **机制**：`key` 初值取当前选中项，**只有 `rect.top <= threshold` 的分组才会覆盖它**。滚回页面顶部时没有任何分组越线 → 选中态停在下滑时到达的最后一天。
- **表现**：内容已回到 10月2日，顶部仍高亮 10月5日。点一下日期可自愈（手动点不经过该函数）。
- **与设计不符**：`产品文档.md:227` 要求「用户下滑时顶部日期选中态随滚动联动」——当前是单向的。

### 5.2 体验层问题

**【P2】完全未适配微信字体大小——与产品自我定位冲突**

- 全项目 **0 处**读取 `fontSizeSetting` / `fontSizeScaleFactor` / `getAppBaseInfo`。
- `font-size` **343 处全部用 `rpx`，0 处用 `px`**。而 `rpx` 是屏宽比例单位，**不随微信字体设置缩放**。
- 后果：用户在微信里开启**关怀模式（×1.4）**，本小程序字号**纹丝不动**。
- **为什么这条重要**：`data/spots.json` 里 **26 个景点有 18 个**带 `audienceTags: ["elder"]`——产品把老年人当核心受众，却完全不响应微信的字体放大。官方有专门的《小程序适老化设计指南》和《无障碍设计指南》。
- 注：这是官方**建议**项，非审核硬性要求，故为 P2。

**【P2】合规清单对「剪贴板」的声明与代码不符**

- `docs/legal/微信审核合规清单.md:40` 声明：地理位置、相机、麦克风、通讯录、相册读取、日历、**剪贴板** → 「当前代码未调用」→「平台不勾选」。
- 实际代码有 **6 处 `wx.setClipboardData`**：`components/spot-popup/spot-popup.js:150,159,178`、`pages/spot-rule/spot-rule.js:73,82,98`。
- **性质**：均为「跳转失败时复制官网链接」的降级兜底，或用户主动点「复制」。**属于写入，不读取用户数据**，不触发授权，因此**不是隐私合规硬伤**。
- **但风险实在**：若按「未调用」去填后台，而审核侧认为需要声明，就是一次提审驳回。且该清单 §128 自己把「剪贴板」列为触发复核的接口——**文档内部自相矛盾**。
- **建议**：把清单第 40 行的表述改为「调用 `setClipboardData`（写入，不读取）」，后台是否勾选按微信当期要求确认。同步核对 `docs/legal/隐私政策.md:39` 的措辞。

**【P2】无障碍几乎为零**

- **129 个 `bindtap`、20 个 `image`，全项目仅 1 处 `aria` 属性，0 个 `aria-label`**。官方建议为可点击 view 补 `aria-role="button"` 与 `aria-label`。读屏用户无法辨识这些入口。

**【待确认】图标尺寸用 px**：99 处 `size="Npx"` vs 9 处 `size="rpx"`。在 375（=750/2）基准机型上二者等价，**其他机型是否等比例缩放，官方 WXSS 文档未明确说明**。列为真机核对项，不作结论。
