# 云开发数据库索引与集合权限清单

> 2026-08-30 与 `cloudfunctions/notifier` 时间窗分页扫描同步整理；2026-09-13 补「集合权限」章节并校对索引字段（换号迁环境时按本页执行）。
> **部署顺序提醒**：先在本页建完「必须」索引，再重新部署 `notifier` 云函数，否则 `notifier` 新的 `where + orderBy('releaseAt')` 查询会因缺索引直接报错。

## 一、集合与权限（云开发控制台 → 数据库 → 新建集合）

本项目**小程序端不直连数据库**（全仓无 `wx.cloud.database()`，数据全走 `wx.cloud.callFunction`），而云函数用管理端凭据读写、**不受集合权限限制**。因此 8 个集合一律选 **「仅管理端可读写」**：功能完全不受影响，同时把所有小程序端直连入口关死，最安全。

| 集合 | 用途 | 权限 |
| --- | --- | --- |
| `spots` | 26 个景点主数据 | 仅管理端可读写 |
| `release_rules` | 放票规则（原 `rules`，**不要再建 `rules`**） | 仅管理端可读写 |
| `users` | 用户资料 + 订阅消息额度台账（按 `openId`） | 仅管理端可读写 |
| `trips` | 行程（按 `userId`） | 仅管理端可读写 |
| `reminder_tasks` | 提醒任务 | 仅管理端可读写 |
| `reminder_cart` | 提醒清单 | 仅管理端可读写 |
| `search_history` | 搜索历史 | 仅管理端可读写 |
| `feedbacks` | 意见反馈 + 信息纠错（TABLE-008） | 仅管理端可读写 |

- 权限四档（控制台原文，从宽到紧）：仅创建者可写，所有人可读 / 仅创建者可读写 / 仅管理端可写，所有人可读 / **仅管理端可读写**。
- 已废弃集合：`favorites`（收藏功能已下线，不要建）。
- ⚠️ **云存储权限不要跟着设成「仅管理端可读写」**：头像是小程序端 `wx.cloud.uploadFile` 直传的（`profile-edit.js` → `avatars/{ts}_{rand}.{ext}`），必须保留客户端写权限，用默认的「所有用户可读，仅创建者可读写」。

## 二、必须（云开发控制台 → 数据库 → 对应集合 → 索引 → 新建）

字段均**升序**、**不勾唯一**。

| 集合 | 索引字段（按顺序） | 服务对象 |
| --- | --- | --- |
| `reminder_tasks` | `backendStatus` + `releaseAt` | notifier 时间窗扫描、sweepMissed 判 MISSED（`where` 等值 + `orderBy('releaseAt')`） |
| `reminder_tasks` | `userId` + `tripId` | `task.list(tripId)`、`task.clear(tripId)`、`timeline.generate` 级联 |
| `reminder_cart` | `userId` + `tripId` | `cart.list(tripId)`、`cart.clear(tripId)` |
| `trips` | `userId` | `trip.list`、`trip.createOrMerge` 查已存在行程 |

> ⚠️ **`reminder_tasks` 的 `backendStatus` + `releaseAt` 是「提醒能不能发出去」的前置条件，缺了就是静默故障**（2026-09-14 线上踩过）。
> 缺这个索引时 `notifier` 的 `fetchTasksPaged` 直接报错；旧版 `tick` 是三步串行，`scanAndSend` 一抛错 `sweepMissed` 就**不会执行**，
> 于是「推送没发出」和「任务没被标 MISSED」同时发生——用户看到的是任务在「已过期」里仍显示「待提醒」，且没有任何失败提示。
> 现已双保险：① `notifier` 的 tick 三步互相隔离（单步失败不影响其余）；② `reminder.task.list` 读取时兜底补判（`sweepOverdue`）。
> 但**索引仍必须建**，否则扫描永远拿不到候选任务，提醒一条也发不出去。

## 三、建议（数据量涨到几千条后再建，避免全表扫）

字段均**升序**、**不勾唯一**。

| 集合 | 索引字段（按顺序） | 服务对象 |
| --- | --- | --- |
| `reminder_tasks` | `userId` | `task.list` 不带行程筛选、`task.clear` 全量 |
| `reminder_tasks` | `userId` + `tripId` + `backendStatus` + `releaseAt` | `trip.list` 取每个行程最近提醒（`where` + `orderBy('releaseAt').limit(1)`） |
| `reminder_tasks` | `backendStatus` + `cleanAt` | `task.cleanup` 自动清理（`where` 两个范围条件，无排序） |
| `users` | `openId` | `user.profile` / `updateProfile` / `updateNotifyPrefs` / `subscribe.add` / `subscribe.get` |
| `search_history` | `userId` + `searchedAt` | `spots.searchHistory`（`where({userId}).orderBy('searchedAt','desc')`） |
| `feedbacks` | `userId` + `createdAt` | `feedback.list`（`where({userId}).orderBy('createdAt','desc')`） |
| `feedbacks` | `createdAt` | `feedback.adminList` 不带 type 筛选时（`where({}).orderBy('createdAt','desc')`）；带 `type` 筛选时用 `type` + `createdAt` |

## 说明

- 云开发数据库索引为「等值 + 排序」复合索引：字段顺序要严格按上面列出，**排序字段必须跟在等值字段之后**。`search_history` / `feedbacks` 原先只列了单字段 `userId`，而实际查询带 `orderBy`，单字段索引带不动排序，故已补全为 `userId` + 排序字段。
- 全部用升序即可：`orderBy('releaseAt','asc')` 由升序索引直接覆盖；`orderBy('searchedAt','desc')` / `orderBy('createdAt','desc')` 可由升序索引反向扫描，**不需要**另建降序索引。
- 「唯一」一律**不勾选**——这些都不是唯一键。
- 单字段索引也要单独建，复合索引不替代它（例如 `reminder_tasks` 同时需要 `userId` 单字段与 `userId + tripId` 复合，二者用途不同，都要建）。
- 建完索引后，`reminder_tasks` 集合总量仍很小时（几百条内）不必急着建全部；4 个「必须」项请先建，因为 `notifier` 部署后即依赖。
