### 0.2 术语表（附录 A 前置，全文强制统一）

| 术语 | 英文 | 定义 |
|---|---|---|
| 行程 | Trip | 一次「城市 + 日期范围」的出行计划，如「北京 5.31-6.4」。是产品的顶层组织单元 |
| 提醒任务 | Reminder Task | 某日某时对某景点的一次放票提醒，是最小执行单元。提交后生成，进入任务列表 |
| 提醒清单 | Reminder Cart | 提交缓冲区（购物车）。选择提醒 → 加入清单 → 可修改 →「开始提醒」后才真正创建任务 |
| 放票规则 | Release Rule | 景点的提前天数、每日放票时间、闭馆日等结构化规则 |
| 预约入口 | Booking Entry | 官方购票渠道（官方小程序 / 官网 / 公众号），提醒后用户手动跳转去抢票 |
| 时间线 | Timeline | 按放票时间点组织的提醒事件序列，是核心信息呈现方式 |

禁止混用「任务 / 订单 / 提醒 / 收藏」等词指代上述概念。

### 0.3 全局强制约定

- `TIME-RULE-001`：全系统时间统一使用北京时间（GMT+8），前后端、云函数、ICS 生成、倒计时展示一律以 GMT+8 计算，避免海外用户出现「提前一天提醒」。
- `UI-001`：视觉实现以 `figma_design.md` 为唯一视觉规范（色彩 Token、字号、圆角、阴影、动效、文案语气）。本说明书只定义结构与行为，不重复视觉参数。
- `UI-002`：文案语气保持安静、克制、带书卷感（`figma_design.md` 第 1 节视觉定位），禁止机器腔（如「暂无数据」「Loading...」）。具体文案以本说明书各页条目内的引号文案为准；新版设计规范已精简，不再包含文案表。

## 第一册 产品需求文档（PRD）

### 1.1 产品定位

- 定位：**旅游景点预约提醒工具 / 景点抢票闹钟**。极致的抢票信息聚合与提醒工具。
- 业务边界：纯粹的实时信息同步与闹钟式提醒。用户收到提醒后**手动跳转官方渠道抢票**，不涉及代抢代约，不保证抢票成功（需在显著位置声明）。
- 目标用户：已完成机酒预订、行程基本确定的自由行游客。核心诉求：不遗漏放票时间、快速同步复杂预约规则、自动化提醒抢票。
- 不服务：模糊规划阶段、泛旅行内容浏览、AI 行程推荐（V1.x 均不做）。
- 核心价值：用户不需要记忆复杂预约规则，也不会再错过任何一个景点的开票时间。

### 1.2 产品原则

- `P-001` **一个行程只关心一件事：按时预约。** 不引入攻略、社区、AI 规划等干扰。
- `P-002` **时间线优先，而不是景点优先。** 以放票时间轴组织信息，而不是以景点组织信息。
- `P-003` **提醒事件是最小执行单元。** 不是景点、不是行程，而是「某一天某时对某景点的一次提醒」。
- `P-004` **尽可能降低用户决策成本。** 自动合并行程、自动生成时间线、自动排序、自动过滤不可选项。

### 1.3 MVP 范围（V1.0）

做：

1. 行程建立（城市 + 日期范围），同城市自动合并（TRIP-RULE-002）。
2. 想去景点选择与搜索（北京 10 个热门景点初始库，见 `data/spots.json`）。
3. 预约时间线自动生成（TIMELINE-RULE-001），按出发日 / 按景点双视图。
4. 提醒清单（购物车）→ 提醒设置 → 提交生成提醒任务。
5. 提醒任务列表（行程分组、进行中 / 已过期筛选、删除）。
6. 提醒触达：公众号订阅消息 + 手机日历 ICS 双通道。
7. 预约入口汇总与跳转（官方小程序直跳，兜底复制链接）。
8. 景点信息弹窗（标签 + 预约方式 + 须知）。
9. 我的页（通知设置、使用攻略、意见反馈、信息纠错）。

不做（明确出界）：会员 / 积分体系（V1.1）、短信提醒（V1.1，UI 置灰「敬请期待」）、余票监控与捡漏（V2）、智能备选景点（V2）、多城市（V1 仅北京，UI-003）、代抢代约（永久红线）。

### 1.4 信息架构（IA）

├── 提醒（= 首页，双形态）
│   ├── 形态1 PAGE-001：无任务时 → 创建入口（日期+景点+生成时间线）
│   └── 形态2 PAGE-009：有任务时 → 提醒任务列表（行程分组 Tab）
│       └── 新增提醒 → PAGE-005 添加提醒页（二级）
├── 我的 PAGE-010
二级页面
├── 想去景点 PAGE-003 / 搜索态 PAGE-004
├── 添加提醒 PAGE-005（出发日视图）/ PAGE-006（景点视图）
└── 设置提醒 PAGE-008

首页形态切换 `HOME-RULE-001`：当前用户无任何提醒任务（或任务全部清空）→ 形态1；存在 ≥1 条任务 → 形态2。

### 1.5 核心流程

`FLOW-001` 首次使用主流程：
进入首页形态1 → 选择行程日期范围 → 选择想去景点（内联热门景点卡 + PAGE-003 补充）→ 点击「生成预约时间线」→ 进入 PAGE-005 时间线 → 逐条「添加提醒」或「一键全部提醒」入清单 → 底部清单条打开 PAGE-007 核对 / 修改 → 「开始提醒」→ PAGE-008 设置提醒方式与提前量 → 提交 → 创建任务 + 同步 ICS + 引导公众号授权 → 首页切换为形态2。

`FLOW-002` 提醒触发流程：
云函数定时扫描 WAITING 任务 → 按用户设置的提前量（放票前 5 分钟 / 2 分钟）触发 → 30 秒内错峰推送（REMINDER-RULE-003）→ 公众号订阅消息 + （日历由 ICS 本地承担）→ 写真实状态 TRIGGERED；超过放票时间点未触发成功 → 写 MISSED；前端 UI 二者均显示「已提醒」（STATE-002）。

`FLOW-003` 抢票跳转流程：
时间线 / 任务中「立即预约」或弹窗预约入口 → 有 officialAppid 则 `wx.navigateToMiniProgram` 直跳 → 无小程序或跳转失败 → 兜底：复制官网链接 + 操作截图引导（ERROR-1007 处理）。

`FLOW-004` 管理流程：
任务三点菜单 → 删除确认 Dialog（文案「确认移除这条提醒？」）→ 删除任务；行程内任务删光 → 行程自动删除（TRIP-RULE-004）；任务已提醒后 14 天自动清理（REMINDER-RULE-006）。

### 1.6 版本规划

- **V1.0（本说明书）**：上述 MVP。核心指标：DAU、提醒提交数、提醒触发成功率。
- **V1.1**：会员 / 积分体系（PAGE-11 形态）、短信提醒通道、订阅合集引导优化。
- **V2**：余票监控（捡漏）、智能备选方案（目标景点约满推荐附近替代）、公众号 / 群机器人通知扩展。
- **V3**：AI 路线规划、景区热力图、分级付费提醒。

## 第二册 UI 与交互规范

> 页面编号与 Figma 导出编号一致：`UI-V1.0/01.png` ~ `11.png` 对应 PAGE-001 ~ PAGE-011，其中 06 未导出（见附录 D）。视觉参数一律查 `figma_design.md`，本册只写结构、行为与状态。

### PAGE-001 提醒首页 · 形态1（创建态）

- 页面目标：无任务时引导用户建立行程并生成时间线。
- 结构（自上而下）：① 顶部栏：左侧城市入口「游北京」（UI-003），中标题「景点预约提醒」；② 行程日期模块「在北京玩几天？」日期范围选择器，占位文案「来北京玩第一件事是预约景点」；③ 想去景点模块「选择哪些地方玩？」已选景点 tag 行，占位文案「北京必游：故宫博物院、国博」；④ 主按钮「生成预约时间线」；⑤ 「北京热门景点预约状态」双列卡片网格；⑥ 底部「+ 选择更多意向景点」→ PAGE-003；⑦ 辅助文案「为你生成专属抢票时间线」。
- 景点卡片：图 + 名称（可点，UI-004 弹窗）+ 难度标签（极难约 / 较难约 / 容易约）+ 标签行「提前7天 每日20:00点放票」+ 右上「选择 / 已选」切换按钮。
- 交互：
  - 日期选择器打开双日期 picker，选定后右侧自动显示「共N天」。
  - 「选择」将景点加入当前行程想去列表，变「已选」；再点取消。
  - 日期或景点为空时点主按钮 → Toast「先选择行程日期和想去景点吧」（UI-005 校验）。
  - 校验通过 → 生成时间线并进入 PAGE-005。
- 异常：景点库加载失败 → 空状态插画 + 「网络开小差了，点击重试」。
- 跳转：PAGE-003 / PAGE-005 / PAGE-002（弹窗）。

### PAGE-002 景点信息弹窗（BottomSheet）

- 触发：`UI-004` 除提醒清单页（PAGE-007）外，所有页面的景点名称均可点击，点击弹出本弹窗。
- 结构：① 头图 + 景点名 + 难度标签；② 标签行：提前N天放票、每日HH:MM放票（核心标签，TAG-RULE-001）；③ 预约方式列表（固定 3 行）：微信公众号（动作：查看二维码）、景区官网（打开链接）、官方小程序（打开链接 / 直跳）；每行含方式说明微文案（如「点击参与预约 → 填写信息 → 预约成功」）；④ 预约注意事项（bookingTips，折叠展开）。
- 交互：蒙层点击 / 下滑关闭；「打开链接」用 web-view 或复制兜底；「官方小程序」走 FLOW-003。
- 异常：某渠道缺失（如 officialAppid 为空）→ 该行隐藏，不显示空行。

### PAGE-003 想去景点页

- 页面目标：补充 / 管理当前行程的想去景点。
- 结构：① 搜索框（进入搜索态 PAGE-004）；② 「已选景点 (N)」横排缩略卡，右上 × 移除，右侧清空按钮；③ 「历史搜索」tag 行（SEARCH-RULE-002）+ 清空；④ 「热门景点」列表（换一批按钮：本地随机洗牌，不请求接口）；列表行 = 图 + 名称 + 标签行 + 「选择 / 已选」按钮。
- 交互：选择 / 已选逻辑同 PAGE-001；移除 / 清空即时生效并 Toast 轻提示；名称点击 → PAGE-002。
- 返回：左上返回，已选结果带回上一页。

### PAGE-004 想去景点 · 搜索态

- 触发：PAGE-003 搜索框聚焦 / 输入。
- 结构：搜索框（含「搜索」按钮）+ 结果列表（行结构同 PAGE-003 列表行）。
- 交互：`SEARCH-RULE-001` 按名称 / 别名 / 拼音前缀本地模糊匹配（V1 景点库为本地静态数据）；提交搜索后写入历史（去重、最多 10 条、最新在前）；无结果 → 空状态「没有找到相关景点，换个词试试」。

### PAGE-005 添加提醒页 · 出发日视图

- 页面目标：展示行程时间线，完成提醒选择与提交。首页形态1「生成预约时间线」与形态2「新增提醒」均进入本页（内容一致）。
- 结构：① 行程摘要：日期范围卡（共N天）+ 想去景点 tag 行（共N个，可点回 PAGE-003 修改）；② 主按钮「生成预约时间线」（行程修改后需重新生成，TIMELINE-RULE-002）；③ 「专属预约时间线」区：右上视图切换「按出发日 / 按景点」+ 批量提醒按钮（文案随视图变，见下）；④ Tab 行（**单选筛选**，出发日视图 = 行程内每日一个 Tab 如「5月31日 周日」；景点视图 = 每个想去景点一个 Tab）；⑤ 时间线主体：仅显示当前选中 Tab 下的事件，左轴为放票时间点（如「5月24日 20:00」「今天 12:00」），右侧事件卡 = 可约状态标签 + 景点名（可点，UI-004）+ 难度标签 + 「M月D日 (周X) 门票」+ 右侧动作按钮；⑥ 底部清单条：清单 icon（角标=清单条数）+「已选 N 项，覆盖 M 个景点」+「开始提醒」按钮。
- 事件卡动作按钮四态（TIMELINE-RULE-004 / STATE-003）：
  - 「+ 添加提醒」：可选，点击加入清单；
  - 「已加清单」：在清单中，不可再选，点击可打开 PAGE-007 查看；
  - 「待提醒」：已提交为任务，不可再选；
  - 「立即预约」：该景点该日已放票（releaseAt ≤ now 且可约），点击走 FLOW-003，不入清单；已约满则按钮置灰「已约满」。
- 交互：
  - 批量提醒按钮仅作用于当前 Tab（CART-RULE-004）：出发日视图下文案「本日全部提醒」，景点视图下「该景点全部提醒」；点击后该 Tab 内所有「+ 添加提醒」态按钮变「已加清单」。
  - 切换 Tab 只换筛选条件，不重新生成时间线、不清空清单。
  - 清单条 icon 点击 → PAGE-007；「开始提醒」→ PAGE-008（清单为空时 Toast「先添加至少一条提醒」）。
  - 时间线默认滚动位置 = 当前 Tab 内最近的未提醒事件；上划浏览更早 / 已提醒内容，超过一屏出现「回到底部」浮窗按钮，点击回到默认位置（UI-006，双向同理）。
- 异常：当前 Tab 无可用事件（如该日全部景点闭馆）→ 空状态「这一天暂无可提醒的放票时间」；行程内全无事件 → 「该行程暂无可提醒的放票时间」。

### PAGE-006 添加提醒页 · 景点视图

- 与 PAGE-005 同页，视图切换为「按景点」：Tab 为想去景点，选中某景点后显示该景点在各出行日的放票事件，组内按 releaseAt 升序；其余模块、按钮、状态完全一致。
- 用途：回答「这个景点哪天的票好抢」——用户看完该景点在行程内各天的放票时间后，再决定哪天去。
- 说明：Figma 导出截图未提供 06 帧，本页按 PAGE-005 视图切换控件推导；如与 Figma 源文件冲突，以 Figma 为准并回改本条。

### PAGE-007 提醒清单（BottomSheet）

- 页面目标：提交缓冲区核对与修改（CART-RULE-001）。
- 结构：① 头部「提醒清单：共N项」+ 右侧「清空」；② 按放票日期分组列表（如 5月24日），行 = 放票时间（含「还剩XXh XXm」倒计时，<1h 变紧急色）+ 景点名 + 「约 M月D日 (周X) 门票」+ 右侧删除（垃圾桶）；③ 底部「已选 N 项，覆盖 M 个景点」+「开始提醒」。
- 交互：删除单条即时生效；清空需 Dialog 确认；「开始提醒」→ PAGE-008；下滑蒙层关闭，清单保留（缓冲不清空）。
- 注意：本页景点名为纯文本，不可点（UI-004 的唯一豁免）。

### PAGE-008 设置提醒页

- 页面目标：提交前设置提醒方式与提前量。
- 结构：① 「提醒方式」卡：公众号提醒（副文案「需打开微信通知权限」，勾选框）、日历提醒（勾选框）、短信提醒（置灰「敬请期待」）；② 「提醒时间」卡：放票前 5 分钟、2 分钟，多选勾选；③ 主按钮「提交」。
- 交互：
  - 方式与提前量至少各选 1 项，否则提交 Toast 校验。
  - 提交成功 → 按 CART-RULE / REMINDER-RULE 创建任务、同步 ICS、触发公众号订阅授权引导 → Toast「提醒已设置，放票前见」→ 返回并刷新为首页形态2。
  - 公众号未授权时：提交不阻塞，弹授权引导弹窗（软引导，可跳过；跳过则仅日历通道生效）。

### PAGE-009 提醒首页 · 形态2（任务列表）

- 页面目标：承载全部提醒任务的查看与管理。

## 第三册 开发实现规范

### 3.1 技术架构

```
前端：微信原生 + Vant Weapp
后端：腾讯云开发（云函数 + 云数据库 NoSQL）
云函数：scraper（抓取）/ notifier（推送）/ spots（查询+状态计算）/ ics-generator（.ics 生成）
抓取：云函数 Playwright + stealth 插件（V1 仅抓有官网的景点）
```

数据源策略：V1 优先抓取有官网网页版的景点（`hasWebVersion: true`，见 spots.json）；抓取失败云函数告警开发者；前端预留「信息纠错」众包入口。反爬对策（stealth、住宅代理、指纹随机、分时段频率）沿用旧版技术方案，属运维实现细节，不在本说明书展开。

### 3.2 行程规则

- `TRIP-RULE-001` 行程 = { 城市, startDate, endDate }，由首页形态1 / 添加提醒页创建。
- `TRIP-RULE-002` 行程合并：新增行程与已有行程同城市，且（日期有交集 或 首尾相接即一方 endDate+1天 = 另一方 startDate）→ 自动合并，日期取并集，并重新生成时间线（TIMELINE-RULE-002）；否则创建新行程。例：北京5.31-6.4 + 6.5-6.8 → 5.31-6.8；5.31-6.4 + 6.6-6.8 → 两个行程。
- `TRIP-RULE-003` 行程命名 = 城市 + 日期范围（如「北京 5.31-6.4」），系统自动生成，用户不可编辑。
- `TRIP-RULE-004` 行程自动删除：行程下提醒任务全部删除 / 清理后，行程自动删除。
- `TRIP-RULE-005` 行程排序：按「最近一条待提醒任务的提醒时间」升序排，最近者排第一；无待提醒任务的行程沉底。
- `TRIP-RULE-006` 分组 Tab 显示：仅 1 个行程时不显示分组行（列表即该行程）；≥2 个时显示「全部 + 各行程 Tab」。

### 3.3 时间线生成规则

- `TIMELINE-RULE-001` 事件生成（**交叉积**）：对行程内每个已选景点 S（规则 R = advanceDays, releaseTime, closedDays）× 行程日期范围内每个非闭馆日 D，生成一个事件：visitDate = D；releaseAt = (D − advanceDays) 当日 releaseTime（GMT+8）；事件 = { spot, visitDate, releaseAt }。事件总数 = Σ(每景点的非闭馆日数)。用户通过视图 Tab 选择实际要哪一天的提醒，产品不替用户推断出行日（变更：2026-08-04 原规则取「范围内第一个非闭馆日」，导致 N 个景点的提醒全部指向行程首日，用户无法表达「哪天去哪个景点」且无修改入口，会抢到错误日期的票）。
- `TIMELINE-RULE-002` 重算时机：行程日期变化、景点增删、合并发生时，整条时间线重新生成；已在清单 / 已提交的事件按 (spotId+visitDate) 保留其状态，被移除景点或落在新范围外的事件自动出清单。
- `TIMELINE-RULE-003` 视图（二者均为**单选筛选**，一次只显示选中项下的事件，不同屏平铺全部交叉积）：按出发日 = 以 visitDate 为 Tab，选中某日 → 显示该日全部景点的放票事件，组内按 releaseAt 升序；按景点 = 以 spot 为 Tab，选中某景点 → 显示该景点在各出行日的放票事件，组内按 releaseAt 升序。
- `TIMELINE-RULE-004` 事件状态判定（渲染按钮四态）：releaseAt > now 且不在清单且未提交 → 「+ 添加提醒」；在清单 → 「已加清单」；已提交 → 「待提醒」；releaseAt ≤ now → 查询实时放票状态：可约 → 「立即预约」，约满 → 置灰「已约满」。
- `TIMELINE-RULE-005` 闭馆日（**按日判定**）：某景点在某日闭馆 → 该 (景点, 日) 不生成事件，其余日期照常生成；若该景点在行程范围内每一天都闭馆，则完全不生成事件，想去列表该行标注「行程期间闭馆」。


### 3.4 提醒清单规则

- `CART-RULE-001` 清单是提交缓冲区：加入 / 删除 / 清空只改缓冲区，不创建任务、不写 ICS。
- `CART-RULE-002` 聚合展示：「已选 N 项，覆盖 M 个景点」，N=清单条数，M=去重景点数。
- `CART-RULE-003` 清单持久化：按用户存云数据库（TABLE-007），跨设备 / 重启不丢；提交成功后对应条目清除。
- `CART-RULE-004` 一键全部提醒：**仅作用于当前选中的 Tab**，不跨 Tab 批量。出发日视图下按钮为「本日全部提醒」，加入该日全部 SELECTABLE 事件；景点视图下为「该景点全部提醒」，加入该景点各出行日的全部 SELECTABLE 事件（适用于「哪天都行、先都提醒着」）。禁止一次加入整条时间线的交叉积（变更：2026-08-04 随 TIMELINE-RULE-001 改为交叉积，原文「当前时间线下所有 SELECTABLE」会一次加入数十条，等于替用户决定每个景点都去每一天）。

- `CART-RULE-005` 入口：PAGE-005/006 底部清单条 icon 打开 PAGE-007。

### 3.5 提醒任务规则

- `REMINDER-RULE-001` 提醒时间点 = releaseAt − offset，offset ∈ 用户勾选的提前量集合（5 分钟 / 2 分钟，可多选，每值各触发一次）。
- `REMINDER-RULE-002` 通道：公众号订阅消息 + 手机日历 ICS。短信 V1.1。
- `REMINDER-RULE-003` 错峰推送：同一放票时间点的批量任务在 30 秒窗口内错峰发送，避免官方接口拥堵。
- `REMINDER-RULE-004` 状态写入：实际发送成功 → TRIGGERED；超过 releaseAt 仍未成功 → MISSED；前端「已过期」筛选包含 MISSED；UI 标签层二者均显示「已提醒」。
- `REMINDER-RULE-005` 任务删除：仅待提醒（WAITING）任务可删；删除同步删除对应未触发的 ICS 事件（ICS-RULE-001）。
- `REMINDER-RULE-006` 自动清理：任务进入 TRIGGERED / MISSED 后 14 天自动删除（CLOSED），触发行程级联检查（TRIP-RULE-004）。
- `REMINDER-RULE-007` Tab 角标 = 未来 24 小时内 WAITING 任务数。
- `REMINDER-RULE-008` Banner：优先级 ① 即将开始提醒（存在 releaseAt − offset 在 1 小时内的任务时展示，文案含景点名与剩余时间）② 系统公告 ③ 活动公告；一次仅展示一条。

### 3.6 ICS 同步规则

- `ICS-RULE-001` 提交时由 ics-generator 生成 / 更新 .ics：每个任务一个事件，标题「{景点}放票提醒」，时间 = releaseAt − offset，备注含预约入口链接；删除待提醒任务 → 同步删除 ICS 事件；已提醒事件保留为历史。
- `ICS-RULE-002` 同步失败不阻塞微信侧提醒，仅 Toast「日历同步失败，可稍后在设置中重新同步」。

### 3.7 搜索 / 排序 / 其它规则

- `SEARCH-RULE-001` 本地模糊匹配：名称 / 别名 / 拼音前缀，V1 不请求服务端。
- `SEARCH-RULE-002` 历史最多 10 条，去重、最新在前，可单条不可（仅整组清空）。
- `SORT-RULE-001` 热门景点网格 / 列表排序 = popularityScore 降序；预约入口排序 = 直达率（官方小程序 > 公众号 > 官网）。
- `TAG-RULE-001` 景点标签：V1 核心标签 = 「提前N天放票」「每日HH:MM放票」+ 难度标签（difficultyScore ≥4 极难约 / 3 较难约 / ≤2 容易约）；弹窗内追加展示闭馆规律、票价、证件要求（取自 rules.json 的 closedDays / ticketPrice / idRequirement），作为「预约注意事项」文本。标签选取原则：只保留帮助用户判断「什么时候抢、难不难抢」的信息，营销性标签一律不上。

### 3.8 页面生命周期

- 首页 onShow：刷新任务列表、Banner、角标；形态判定 HOME-RULE-001。
- 添加提醒页 onShow：行程或想去列表变化 → TIMELINE-RULE-002 重算；否则用缓存。
- 时间线倒计时：前端本地秒级倒计时，基准为服务端 GMT+8 时间戳（进入页面时校时一次）。
- 提交页提交中：按钮 Loading「正在为您查询…」风格，防重复提交。
- 我的页 onShow：刷新通知授权状态文案。

### 枚举与状态机

- `ENUM-001` TripStatus：ACTIVE（进行中）/ FINISHED（全部任务已完成或过期）。
- `ENUM-002` ReminderBackendStatus：WAITING / TRIGGERED / MISSED / CLOSED。
- `ENUM-003` EventSelectStatus（时间线按钮态）：SELECTABLE / IN_CART / WAITING / REMINDERED / BOOKABLE / FULL。
- `ENUM-004` ChannelType：OFFICIAL_ACCOUNT / CALENDAR_ICS / SMS（reserved）。
- `ENUM-005` ReleaseStatus（实时放票状态）：NOT_RELEASED / BOOKABLE / FULL。
- `ENUM-006` DifficultyLabel：三挡，与 TAG-RULE-001 同一阈值 —— EXTREME(difficultyScore ≥4)「极难约」/ NORMAL(=3)「较难约」/ EASY(≤2)「容易约」。注：`data/spots.json` 现有 10 个景点的 difficultyScore 实际只用了 {1,2,3,5}。

- `STATE-001` 后台提醒状态机：WAITING →（发送成功）TRIGGERED →（+14d）CLOSED；WAITING →（超时未触发）MISSED →（+14d）CLOSED；WAITING →（用户删除）直接物理删除。
- `STATE-002` UI 状态映射：WAITING → 「待提醒」；TRIGGERED / MISSED → 「已提醒」；CLOSED → 不展示。
- `STATE-003` 选择状态机：SELECTABLE →（加入清单）IN_CART →（提交）WAITING →（完成）REMINDERED；IN_CART / WAITING / REMINDERED 均不可再次选择；SELECTABLE →（releaseAt 到达且可约）BOOKABLE（转「立即预约」，脱离清单体系）。
