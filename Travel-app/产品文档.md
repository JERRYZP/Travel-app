## 第一册 产品需求文档（PRD）

### 1.1 产品定位

- 定位：**旅游景点预约提醒工具 / 景点抢票闹钟**。极致的抢票信息聚合与提醒工具。
- 业务边界：纯粹的实时信息同步与闹钟式提醒。用户收到提醒后**手动跳转官方渠道抢票**，不涉及代抢代约，不保证抢票成功（需在显著位置声明）。
- 目标用户：已完成机酒预订、行程基本确定的自由行游客。核心诉求：不遗漏放票时间、快速同步复杂预约规则、自动化提醒抢票。
- 不服务：模糊规划阶段、泛旅行内容浏览、AI 行程推荐（V1.x 均不做）。
- 核心价值：用户不需要记忆复杂预约规则，也不会再错过任何一个景点的开票时间。

### 1.2 产品原则

- `P-001` **一个行程只关心一件事：按时预约。** 不引入攻略、社区、AI 规划等干扰。
- `P-002` **出行日轴优先。** 首页按 `visitDate` 组织行程项，放票时刻降为行程项属性；不再以放票日作为首页主轴。
- `P-003` **行程项是最小执行单元。** 不是景点、不是行程，而是「哪个行程 + 哪个景点 + 哪一天」；提醒任务挂在行程项下。
- `P-004` **尽可能降低用户决策成本。** 自动生成时间线、自动排序、自动过滤不可选项；时间上连续/重叠的行程自动合并成一个分组。（变更：2026-09-14 恢复自动合并行程——靠「各景点保留自己的日期段」避免时间线出现用户没选的日期/景点，撤销 2026-08-31 的「取消自动合并」）

### 1.3 MVP 范围（V1.0）

做：

1. 行程建立（城市 + 日期范围），同城市且日期相交/相接的行程自动合并为同一行程分段；间隔至少一天为新行程（TRIP-RULE-002）。
2. 想去景点选择与搜索（北京 26 个景点库 = 需预约 19 + 免预约 7）。免预约景点可加入行程、必须选择具体日期，但不进入提醒流程；可提醒景点为 18 个。环球影城需预约但无固定放票时刻，V1 暂不可选。
3. 排期时间线自动生成（TIMELINE-RULE-001），按出发日 / 按景点双视图；免预约景点只选日期，不生成放票事件。
4. 购物车统一加入行程：需预约项可勾提醒，免预约项固定不提醒；存在提醒项时进入设置页后统一提交。
5. 行程状态墙：六状态、票务结果回填、提醒未送达警示、备选收束与挽回动线；不保留独立提醒任务列表。
6. 提醒触达：公众号订阅消息（V1.1 短信；手机日历 ICS 已于 2026-08-14 下线，ICS-RULE 保留为遗留规则）。（变更：2026-08-26 标注日历通道已下线）
7. 预约入口汇总与跳转（官方小程序直跳，兜底复制链接）。
8. 景点信息弹窗（标签 + 预约方式 + 须知）。
9. 我的页（通知设置、使用攻略、意见反馈、信息纠错）。

不做（明确出界）：会员 / 积分体系（V1.1）、短信提醒（V1.1，UI 置灰「敬请期待」）、余票监控与捡漏（V2）、智能备选景点（V2）、多城市（V1 仅北京，UI-003）、代抢代约（永久红线）。

`HOME-RULE-001`（2026-09-16 覆盖旧双形态）：首页只有行程状态墙一种形态，不再按“有无任务”切换，不保留“提醒任务 / 添加提醒”双 Tab，不保留放票日轴独立入口。页面自上而下为：全局吸顶放票横幅 → 最近行程全局摘要卡 → 未结束行程纵向分段墙 → 历史行程折叠区。

### 1.5 核心流程

`FLOW-001` 首次使用 / 加入行程：
创建行程日期范围 → 选择想去景点 → 生成排期时间线 → 从具体出行日加入购物车。需预约项可勾选提醒，免预约项固定不提醒。购物车全部不提醒时直接提交；存在提醒项时进入 PAGE-008 配置提醒 → 提交后同时创建行程项和提醒任务 → 返回行程状态墙。

`FLOW-002` 提醒触发与抢票：
云函数按 `itemId` 对应提醒任务发送订阅消息 → 用户点击推送直达对应行程项详情浮窗 → 展示官方预约入口和放票倒计时 → 用户去官方渠道手动抢票。放票后官方预约入口持续保留，直到该 `visitDate` 23:59。

`FLOW-003` 结果回填：
用户在推送详情或行程项右侧菜单标记“抢到了 / 没抢到” → 写入人工结果 → 10 秒内可 Snackbar 撤销 → 抢到且存在备选时询问删除或保留；保留则继续抢。没抢到且已有可用备选时提升下一备选；没有备选时展示行程内候选日期建议。

`FLOW-004` 管理流程：
行程项右侧菜单统一承载标记结果、提醒状态、修改/取消提醒、删除行程项。删除单个行程项 / 某日全部行程项均二次确认；行程下无任何行程项时行程消失。提醒任务不再有独立用户入口，14 天清理仍由后台执行。

`FLOW-005` 抢票跳转流程：
行程项预约入口 → 有官方小程序则直跳，失败或无入口则弹 PAGE-002 选择官网 / 公众号 / 复制链接兜底；V1 不提供代抢、余票监控或付费占位。

### 1.6 首页行程状态墙最终口径（2026-09-16）

六个用户可见状态：`待抢 / 可抢 / 已成 / 未成 / 开过票了 / 免预约`。

- `待抢`：未到放票时间。
- `可抢`：已放票，24 小时内未人工标记。
- `已成 / 未成`：用户人工结果，只能从空状态写一次；10 秒内允许撤销。
- `开过票了`：已放票超过 24 小时且未人工标记，是中性态，不判失败；到 `visitDate` 23:59 前仍可补标记和进入官方预约。
- `免预约`：固定状态，只进行程，不生成提醒。
- 状态在读取时动态推导，`开过票了`不落库，不依赖后台定时任务。
- 票务状态与提醒送达状态分离。提醒未送达在卡片上显示轻量警告 icon，具体原因在右侧菜单查看。
- 行程摘要“门票搞定 N/M”：M = 去重后的预约需求组，同一景点多个备选只算一个；任意日期已成即该需求完成；免预约项不计入分母，另显示“另有 X 处随到随玩”。
- 首页多行程按开始日期纵向排列，不使用横向 Tab。顶部只有一张最近行程摘要卡；其他行程使用紧凑分段标题。历史行程统一折叠在页面底部，结束日次日归入历史。

### 1.7 版本规划

- **V1.0（本说明书）**：上述 MVP。核心指标：DAU、提醒提交数、提醒触发成功率；本次改版验收另看挽回动线使用量和“抢到了”标记量。
- **V1.1**：会员 / 积分体系（PAGE-11 形态）、短信提醒通道、订阅合集引导优化。
- **V2**：余票监控（捡漏）、智能备选方案、公众号 / 群机器人通知扩展。
- **V3**：AI 路线规划、景区热力图、分级付费提醒。

- 页面目标：无任务时引导用户建立行程并生成时间线。
- 结构（自上而下）：① 顶部栏：中标题「景点预约提醒」（有任务时被导航栏双 Tab 替代，见 PAGE-009）；② 行程模块「去哪儿玩几天？」：城市卡「北京」（点击 Toast「更多城市即将开放」，UI-003）+ 日期卡，占位「选择游玩日期」，选定后显示日期范围 + 「共N天」；③ 想去景点模块「去哪些地方玩？」已选景点 tag 行，占位文案「北京必游：故宫博物院、国博」；④ 主按钮「生成预约时间线」；⑤ 「北京热门景点预约状态」双列卡片网格（**只展示 S 级** = 需预约且 difficultyScore≥4，最多 10 个）；⑥ 底部「+ 选择更多意向景点」→ PAGE-003；⑦ 辅助文案「为你生成专属抢票时间线」。（变更：2026-08-26 城市入口/表单文案改为「去哪儿玩几天？」+ 日期占位「选择游玩日期」；2026-08-31 难度 V2 后 S 级缩至 3 个，网格展示 3 个）
- 景点卡片：图 + 名称（可点，UI-004 弹窗）+ 难度标签（极难约 / 较难约 / 容易约）+ 标签行「提前7天 每日20:00点放票」+ 右上「选择 / 已选」切换按钮。
- 交互：
  - 日期选择器打开双日期 picker，选定后右侧自动显示「共N天」。
  - 「选择」将景点加入当前行程想去列表，变「已选」；再点取消。
  - 日期或景点为空时点主按钮 → Toast「先选择行程日期和想去景点吧」（UI-005 校验）。
  - 校验通过 → 生成时间线：无提醒任务时（形态1）内联展示在当前页表单下方，不跳转；时间线过多时滚动上滑，时间线标题区吸顶在导航栏下方。

- 跳转：PAGE-003 / PAGE-002（弹窗）；「生成预约时间线」内联生成不跳转；有任务时通过导航栏「添加提醒」Tab 或任务页悬浮按钮回到本视图（不跳页）。

## 第三册 开发实现规范

### 3.1 技术架构

```
前端：微信原生 + Vant Weapp
后端：腾讯云开发（云函数 + 云数据库 NoSQL）
云函数：reminder（行程/时间线/清单/任务/用户，核心）/ spots（查询+状态计算）/ feedback（意见反馈/信息纠错）/ scraper（抓取）/ notifier（推送）/ ics-generator（.ics 生成，2026-08-14 起日历通道下线，保留但前端无调用）
抓取：云函数 Playwright + stealth 插件（V1 仅抓有官网的景点）
```

数据源策略：V1 优先抓取有官网网页版的景点（`hasWebVersion: true`，见 spots.json）；抓取失败云函数告警开发者；前端预留「信息纠错」众包入口。反爬对策（stealth、住宅代理、指纹随机、分时段频率）沿用旧版技术方案，属运维实现细节，不在本说明书展开。

### 3.2 行程规则

- `TRIP-RULE-001` 行程 = { 城市, startDate, endDate }，由首页创建表单创建；无行程时显示创建引导，有行程时进入状态墙。
- `TRIP-RULE-002` 行程创建**或合并**（2026-09-14 恢复自动合并，撤销 2026-08-31 的「取消自动合并」）：同城市 且（日期有交集 或 首尾相接）→ 合并成同一行程，日期取并集；新行程可能同时与多个既有行程相接，滚雪球式反复合并直到不再变化。首尾相接 = 一方 endDate + 1 天 = 另一方 startDate。示例：北京 5.31-6.4 + 6.5-6.8 → 合并为「北京 5.31-6.8」；北京 5.31-6.4 + 6.6-6.8 → 不合并（隔了 6.5）。
  - **合并的是行程（任务分组），不是景点**：每个景点保留自己被选中时的日期段，存为 `spots: [{spotId, startDate, endDate}]`（`spotIds` 降级为 `spots` 的去重派生字段，供想去列表 / 批量查询用）。所以「北京 9.23-9.24 选故宫 + 北京 9.25-9.26 选国博」合并后：行程 = 北京 9.23-9.26（一个 Tab），时间线 = 故宫 9.23/9.24 + 国博 9.25/9.26，**不会**冒出「故宫 9.25」「国博 9.23」——这正是 08-31 取消合并想避免的问题，现由 `spots` 段解决，无需再牺牲分组。
  - 被吞并行程的任务与提醒清单自动改挂到存续行程（提醒本身不受影响），存续行程复用第一个被合并行程的 tripId，用户无感。
  - 老数据兼容：只有 `spotIds` 的行程按行程整段回退（`normalizeSpots`），与合并前口径等价，线上已有行程无需数据迁移。
  - `adjustTripId`（「在当前内联时间线的行程上重新生成」）：该行程的景点段按本次输入**替换**（而非并集），其余被并进来的行程段保留；仍会与其它日期相交/相接的行程继续合并。日期与本次输入不相交/不相接时按「新建行程」处理，旧行程留原样（空则由 `trip.list` 孤儿清理收走）。
- `TRIP-RULE-003` 行程命名 = 城市 + 日期范围（如「北京 5.31-6.4」），系统自动生成，用户不可编辑。
- `TRIP-RULE-004` 行程删除判定（V2 覆盖旧任务口径）：只按是否还有 `trip_items` 判断。删除行程项 / 删除某日全部行程项后，行程下无任何行程项则行程消失；草稿时间线尚未提交时，行程可由创建流程管理，不再靠任务数决定。旧任务级联代码仅作迁移期兼容。
- `TRIP-RULE-005` 行程排序：按开始日期升序。
- `TRIP-RULE-006` 多行程呈现（V2 覆盖）：不设分组 Tab，按开始日期纵向分段；每段使用紧凑标题，顶部只有最近行程一张完整摘要卡。

### 3.3 时间线生成规则

- `TIMELINE-RULE-001` 事件生成（**交叉积，但按景点自己的日期段**）：对行程内每个已选景点 S（规则 R = advanceDays, releaseTime, closedDays）× **该景点自己的日期段**（`spots` 里的 startDate..endDate；老数据无 `spots` 时回退为行程整段）内每个非闭馆日 D，生成一个事件：visitDate = D；releaseAt = (D − advanceDays) 当日 releaseTime（GMT+8）；事件 = { spot, visitDate, releaseAt }。事件总数 = Σ(每景点在自己段内的非闭馆日数)。**仅需预约且有真实放票时刻的景点生成事件**：reservationRequired=false 的免预约景点不进入时间线/清单/任务（2026-08-10）；需预约但 advanceDays/releaseTime 为空（如环球影城）同样排除，并在时间线下方列出「无固定放票时刻，暂不生成提醒」（2026-08-26）。用户通过视图 Tab 选择实际要哪一天的提醒，产品不替用户推断出行日（变更：2026-08-04 原规则取「范围内第一个非闭馆日」，导致 N 个景点的提醒全部指向行程首日，用户无法表达「哪天去哪个景点」且无修改入口，会抢到错误日期的票）。（变更：2026-09-14 改为按景点自己的段生成——行程合并后不再把「整段 × 全部景点」做交叉积）
- `TIMELINE-RULE-002` 重算时机：行程日期变化、景点增删、重新生成、**行程合并发生**时，整条时间线重新计算；已在清单 / 已提交的事件按 (spotId+visitDate) 保留其状态，被移除景点或落在新范围外的事件自动出清单。（2026-09-14 恢复自动合并后，「合并发生」重新成为一个触发源；因各景点按自己的段并入，合并不会让事件膨胀）
- `TIMELINE-RULE-003` 视图（二者均为**单选筛选**，一次只显示选中项下的事件，不同屏平铺全部交叉积）：按出发日 = 以 visitDate 为 Tab，选中某日 → 显示该日全部景点的放票事件，组内按 releaseAt 升序；按景点 = 以 spot 为 Tab，选中某景点 → 显示该景点在各出行日的放票事件，组内按 releaseAt 升序。
- `TIMELINE-RULE-004` 事件状态判定（渲染按钮四态）：releaseAt > now 且不在清单且未提交 → 「+ 添加提醒」；在清单 → 「已加清单」；已提交 → 「待提醒」；releaseAt ≤ now → 查询实时放票状态：可约 → 「立即预约」，约满 → 置灰「已约满」。
- `TIMELINE-RULE-005` 闭馆日（**按日判定**）：某景点在某日闭馆 → 该 (景点, 日) 不生成事件，其余日期照常生成；若该景点在行程范围内每一天都闭馆，则完全不生成事件，想去列表该行标注「行程期间闭馆」。


### 3.4 提醒清单规则

- `CART-RULE-001` 清单是提交缓冲区：加入 / 删除 / 清空只改缓冲区，不创建任务、不写 ICS。
- `CART-RULE-002` 聚合展示：「已选 N 项，覆盖 M 个景点」，N=清单条数，M=去重景点数。
- `CART-RULE-003` 清单持久化：按用户存云数据库（TABLE-007），跨设备 / 重启不丢；提交成功后对应条目清除。
- `CART-RULE-004` 一键全部提醒：**仅作用于当前选中的 Tab**，不跨 Tab 批量。按钮文案为「一键全部提醒」，加入该日全部 SELECTABLE 事件；景点视图下为「该景点全部提醒」，加入该景点各出行日的全部 SELECTABLE 事件（适用于「哪天都行、先都提醒着」）。禁止一次加入整条时间线的交叉积（变更：2026-08-04 随 TIMELINE-RULE-001 改为交叉积，原文「当前时间线下所有 SELECTABLE」会一次加入数十条，等于替用户决定每个景点都去每一天）。

- `CART-RULE-005` 入口：首页内联时间线底部清单条 icon 打开 PAGE-007 弹窗（当前实现为 cart-popup 组件）。（变更：2026-08-26 PAGE-005/006 已并入首页）

### 3.5 提醒任务规则

- `REMINDER-RULE-001` 提醒时间点 = releaseAt − offset，offset ∈ 用户勾选的提前量（5 分钟 / 2 分钟，单选二选一；一次性订阅消息按条授权，一条任务只发一条提醒）。
- `REMINDER-RULE-002` 通道：公众号订阅消息。手机日历 ICS 已于 2026-08-14 下线（ICS-RULE 保留为遗留规则），短信 V1.1。（变更：2026-08-26 标注日历通道下线）
- `REMINDER-RULE-003` 错峰推送：同一放票时间点的批量任务在 30 秒窗口内错峰发送，避免官方接口拥堵。
- `REMINDER-RULE-004` 状态写入：实际发送成功 → TRIGGERED；超过 releaseAt 仍未成功 → MISSED；发送失败不记 sentOffsets，下一分钟重试；前端「已过期」筛选包含 MISSED；UI 标签：TRIGGERED「已提醒」，MISSED「未送达」。（2026-09-14 补：① 「已过 releaseAt 仍是 WAITING」在读取时即视为 MISSED，`task.list` 兜底补判并落库，不再依赖 notifier 定时链路必须成功；② 发送失败原因写入 `lastSendError`，sweepMissed 优先用它当 `missedReason`，避免「WX_APPSECRET 未配置」「43101 配额不足」这类可行动信息被笼统文案盖掉；③ notifier 的 tick 三步互相隔离，`scanAndSend` 抛错不再连带 `sweepMissed` 不执行）
- `REMINDER-RULE-005` 任务删除：**WAITING 与 MISSED 均可单条删除**；仅 TRIGGERED（已成功送达）保留为历史记录，不允许单删，需走「清空任务」批量清理；删除后任务列表即时刷新，ICS 联动已随日历通道下线（2026-08-14）。（变更：2026-08-26 移除 ICS 联动描述；**2026-09-14 放宽「仅 WAITING 可删」**——过期任务在读取时会被收敛为 MISSED，若仍只允许 WAITING 单删，则「失败的任务反而删不掉」，与「清空任务」能清掉 MISSED/TRIGGERED 的口径也自相矛盾）
- `REMINDER-RULE-006` 自动清理：任务进入 TRIGGERED / MISSED 后 14 天自动删除（CLOSED），触发行程级联检查（TRIP-RULE-004）。
- `REMINDER-RULE-007` Tab 角标（已废弃 2026-08-20）：原定义为未来 24 小时内 WAITING 任务数。因 2 栏 tab、首页直达任务列表，角标与「进行中 N」口径不一致易造成困惑，已整体移除（含 `task.badge` 接口），规则号保留避免后续编号级联。
- `REMINDER-RULE-008` Banner：优先级 ① 即将开始提醒（存在 releaseAt − offset 在 1 小时内的任务时展示，文案含景点名与剩余时间）② 系统公告 ③ 活动公告；一次仅展示一条。

### 3.6 ICS 同步规则

- `ICS-RULE-001`（已下线 2026-08-14，编号保留）提交时由 ics-generator 生成 / 更新 .ics：每个任务一个事件，标题「{景点}放票提醒」，时间 = releaseAt − offset，备注含预约入口链接；删除待提醒任务 → 同步删除 ICS 事件；已提醒事件保留为历史。现状：`setup` 页无日历勾选项、前端 `api.ics` 为空，ics-generator 云函数保留但无调用；若恢复日历通道需重新接线并同步 API-契约。
- `ICS-RULE-002`（已下线 2026-08-14，编号保留）同步失败不阻塞微信侧提醒，仅 Toast「日历同步失败，可稍后在设置中重新同步」。

### 3.7 搜索 / 排序 / 其它规则

- `SEARCH-RULE-001` 本地模糊匹配：名称 / 别名 / 拼音前缀，V1 不请求服务端。
- `SEARCH-RULE-002` 历史最多 10 条，去重、最新在前，可单条不可（仅整组清空）。
- `SORT-RULE-001` 热门景点网格 / 列表排序 = popularityScore 降序；预约入口排序 = 直达率（官方小程序 > 公众号 > 官网）。
- `TAG-RULE-001` 景点标签：V1 核心标签 = 「提前N天放票」「每日HH:MM放票」+ 难度标签（difficultyScore ≥4 极难约 / 3 较难约 / ≤2 容易约）；弹窗内追加展示闭馆规律、票价、证件要求（取自 rules.json 的 closedDays / ticketPrice / idRequirement），作为「预约注意事项」文本。标签选取原则：只保留帮助用户判断「什么时候抢、难不难抢」的信息，营销性标签一律不上。

### 3.8 页面生命周期

- 首页 onShow：调用 `home.bootstrap` V2 刷新当前/未来行程、历史行程、进度、行程项状态与全局 Banner；若用户从推送进入，滚动定位对应 `itemId`。首页不再判定旧形态，也不切换任务 Tab。
- 首页「添加提醒」视图（不单独建页）：生成时间线后保留内联进度；行程或想去列表变化 → TIMELINE-RULE-002 重算，否则用缓存。
- 时间线倒计时：前端本地秒级倒计时，基准为服务端 GMT+8 时间戳（进入页面时校时一次）。
- 提交页提交中：按钮 Loading「正在为您查询…」风格，防重复提交。
- 我的页 onShow：刷新通知授权状态文案。

### 3.11 首页行程化 V2 规则（覆盖冲突旧条目，2026-09-16）

- `TRIP-ITEM-RULE-001` 行程项 = `{ tripId, spotId, visitDate }`，逻辑唯一；同一景点多个备选日期各为一个行程项，共用一个 `backupGroupId`。
- `TRIP-ITEM-RULE-002` 行程项是首页状态墙、票务进度、提醒任务和删除动线的事实来源；行程为空只看是否还有行程项。
- `TRIP-ITEM-RULE-003` 状态在读取时推导：`result` 只持久化人工结果，`UNMARKED` 不落库；放票后 24 小时转“开过票了”。
- `TRIP-ITEM-RULE-004` 人工结果只能从空状态写一次，10 秒内可通过 `tripItem.undoResult` 撤销；之后不可修改。
- `TRIP-ITEM-RULE-005` 放票后官方预约入口持续保留到 `visitDate` 23:59，不因进入“开过票了”或标记“未成”而消失。
- `TRIP-ITEM-RULE-006` 抢到后若有备选：用户删则删除对应行程项及任务；用户保留或不操作则继续按原计划抢票和提醒。
- `TRIP-ITEM-RULE-007` 没抢到后已有可用备选时提升下一备选；没有时展示候选日。候选只判断开放和是否已放票，不承诺实时有余票。
- `TRIP-ITEM-RULE-008` 进度分母按预约需求组去重；同一 `backupGroupId` 内任意行程项已成即完成该组，免预约项不计入分母。
- `TRIP-ITEM-RULE-009` 多行程按开始日期纵向分段，不设横向 Tab。顶部只有最近行程全局摘要卡；其他未结束行程使用紧凑分段标题。历史行程结束日次日读取时归入底部折叠区。
- `TRIP-ITEM-RULE-010` 提醒送达状态 `NOT_SET / WAITING / TRIGGERED / MISSED` 与票务状态分离；MISSED 必须显示轻量警告 icon 和原因入口。
- `TIMELINE-RULE-001` 的新增补充：免预约景点也进入排期时间线并按日期加入行程，但不生成释放事件和提醒。环球影城无固定放票时刻，V1 继续不可选。
- `CART-RULE` 的新增补充：购物车项包含 `remindOn`；弱提醒默认不勾，免预约项固定无提醒。全部不提醒时直接提交；存在提醒项时进入 PAGE-008 后统一提交。
- `REMINDER-RULE` 的新增补充：提醒任务必须挂 `itemId`；用户不再通过任务列表管理提醒。已有任务的票务结果与提醒送达状态必须分开展示。

### 枚举与状态机

- `ENUM-001` TripStatus：ACTIVE（进行中）/ FINISHED（全部任务已完成或过期）。
- `ENUM-002` ReminderBackendStatus：WAITING / TRIGGERED / MISSED / CLOSED。
- `ENUM-003` EventSelectStatus（时间线按钮态）：SELECTABLE / IN_CART / WAITING / REMINDERED / BOOKABLE / FULL。
- `ENUM-004` ChannelType：OFFICIAL_ACCOUNT / SMS（reserved）。CALENDAR_ICS 已于 2026-08-14 移除。（变更：2026-08-26 与 API-契约对齐）
- `ENUM-005` ReleaseStatus（实时放票状态）：NOT_RELEASED / BOOKABLE / FULL。
- `ENUM-007` TicketState（行程项展示态）：PENDING / BOOKABLE / SUCCESS / FAILED / UNMARKED / NO_RESERVATION，依次对应「待抢 / 可抢 / 已成 / 未成 / 开过票了 / 免预约」。
- `ENUM-008` TicketResult（人工结果）：SUCCESS / FAILED；null = 未标记。
- `ENUM-009` ReminderDeliveryState（提醒送达）：NOT_SET / WAITING / TRIGGERED / MISSED，与票务状态分离。
- `ENUM-006` DifficultyLabel：三挡，与 TAG-RULE-001 同一阈值 —— EXTREME(difficultyScore ≥4)「极难约」/ NORMAL(=3)「较难约」/ EASY(≤2)「容易约」。注：现有 26 个景点 difficultyScore 取值 {1,2,3,4,5}；B 层免预约（reservationRequired=false）景点 difficultyScore 不统一（首博、孔庙国子监为 2，其余为 1），UI 不渲染难度标签。

- `STATE-001` 后台提醒状态机：WAITING →（发送成功）TRIGGERED →（+14d）CLOSED；WAITING →（超时未触发）MISSED →（+14d）CLOSED；WAITING →（用户删除）直接物理删除。
- `STATE-002` UI 状态映射：WAITING → 「待提醒」；TRIGGERED → 「已提醒」；MISSED → 「未送达」（附原因解释入口）；CLOSED → 不展示。**判定口径单一**：`backendStatus` 是唯一真身，「已过 releaseAt 的 WAITING」在返回前已被收敛为 MISSED，前端不再自行按时间推算状态（否则会出现「已过期 + 待提醒 + 无图标」的三方不一致）。（变更：2026-09-14）
- `STATE-003` 选择状态机：SELECTABLE →（加入清单）IN_CART →（提交）WAITING →（完成）REMINDERED；IN_CART / WAITING / REMINDERED 均不可再次选择；SELECTABLE →（releaseAt 到达且可约）BOOKABLE（转「立即预约」，脱离清单体系）。V2 首页以 STATE-004 为准。
- `STATE-004` 行程项票务状态机：`NO_RESERVATION`（免预约）｜`PENDING`（未到 releaseAt）｜`BOOKABLE`（releaseAt 到达且 24h 内未标记）｜`UNMARKED`（超过 24h 未标记）｜`SUCCESS` / `FAILED`（人工结果）。状态读取时推导，UNMARKED 不落库。
- `STATE-005` 人工结果状态机：`null` →（抢到了）SUCCESS 或（没抢到）FAILED；10 秒内可撤销回 null；超时后不可修改。
