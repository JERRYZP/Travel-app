## 第一册 产品需求文档（PRD）

### 1.1 产品定位

- 定位：**旅游景点预约提醒工具 / 景点抢票闹钟**。极致的抢票信息聚合与提醒工具。
- 业务边界：纯粹的实时信息同步与闹钟式提醒。用户收到提醒后**手动跳转官方渠道抢票**，不涉及代抢代约，不保证抢票成功（需在显著位置声明）。
- 目标用户：已完成机酒预订、行程基本确定的自由行游客。核心诉求：不遗漏放票时间、快速同步复杂预约规则、自动化提醒抢票。
- 不服务：模糊规划阶段、泛旅行内容浏览、AI 行程推荐（V1.x 均不做）。
- 核心价值：用户不需要记忆复杂预约规则，也不会再错过任何一个景点的开票时间。

### 1.2 产品原则

- `P-001` **检验尺：一个功能若不回答「这张票到手没有 / 怎么让它到手」，就不做。**
  路线、交通、餐厅、攻略、AI 推荐一律出界。（变更：2026-09-20 原「一个行程只关心一件事：按时预约」
  只说了「按时提醒」，管不到「提醒之后票到底拿到没有」——而后者才是用户真正焦虑的那一段）
- `P-002` **出行日轴优先。** 首页按 `visitDate` 组织行程项，放票时刻降为行程项属性；不再以放票日作为首页主轴。
- `P-003` **行程项是最小执行单元。** 不是景点、不是行程，而是「哪个行程 + 哪个景点 + 哪一天」；提醒任务挂在行程项下。
- `P-004` **尽可能降低用户决策成本。** 自动生成时间线、自动排序、自动过滤不可选项；时间上连续/重叠的行程自动合并成一个分组。（变更：2026-09-14 恢复自动合并行程——靠「各景点保留自己的日期段」避免时间线出现用户没选的日期/景点，撤销 2026-08-31 的「取消自动合并」）

### 1.3 MVP 范围（V1.0）

做：

1. 行程建立（城市 + 日期范围），同城市且日期相交/相接的行程自动合并为同一行程分段；间隔至少一天为新行程（TRIP-RULE-002）。
2. 想去景点选择与搜索（北京 26 个景点库 = 需预约 19 + 免预约 7）。免预约景点可加入行程、必须选择具体日期，但不进入提醒流程；可提醒景点为 18 个。环球影城需预约但无固定放票时刻，可加入行程、不可设提醒。（变更：2026-10-28 放开环球影城加入行程）
3. 排期时间线自动生成（TIMELINE-RULE-001），按出发日 / 按景点双视图；免预约景点只选日期，不生成放票事件。
4. 购物车统一加入行程：需预约项可勾提醒，免预约项固定不提醒；存在提醒项时进入设置页后统一提交。
5. 行程状态墙：六状态、票务结果回填、提醒未送达警示、备选收束与挽回动线；不保留独立提醒任务列表。
6. 提醒触达：公众号订阅消息（V1.1 短信；手机日历 ICS 已于 2026-08-14 下线，ICS-RULE 保留为遗留规则）。（变更：2026-08-26 标注日历通道已下线）

### 1.5 核心流程

`FLOW-001` 首次使用 / 加入行程：
创建行程日期范围 → 选择想去景点 → 生成排期时间线 → 从具体出行日加入购物车。需预约项可勾选提醒，免预约项固定不提醒。购物车全部不提醒时直接提交；存在提醒项时进入 PAGE-008 配置提醒 → 提交后同时创建行程项和提醒任务 → 返回行程状态墙。（变更：2026-09-20 ①「生成排期时间线」为**纯预览**，不创建、不改写行程；行程创建与合并判定挪至**提交清单时**执行（TRIP-RULE-002 / TIMELINE-RULE-002 同步改口径）②清单主按钮文案「开始提醒」→「提交行程清单」）

`FLOW-002` 提醒触发与抢票：
云函数按 `itemId` 对应提醒任务发送订阅消息 → 用户点击推送直达对应行程项详情浮窗 → 展示官方预约入口和放票倒计时 → 用户去官方渠道手动抢票。放票后官方预约入口持续保留，直到该 `visitDate` 23:59。

`FLOW-003` 结果回填：
用户在推送详情或行程项右侧菜单标记“抢到了 / 没抢到” → 写入人工结果 → 4 秒内可 Snackbar 撤销 → 抢到且存在备选时询问删除或保留；保留则继续抢。用户本次点击“没抢到”并写入成功后，卡片才立即展示「约其他日」，不等待候选计算；已有 `FAILED` 状态重新加载时不默认显示，只从右侧菜单进入。人工结果写反时，可从右侧三点菜单双向更正：未抢到 → 已抢到、已约到 → 未约到；撤销会恢复修改前结果。有候选时展示候选提示，没有候选时用户仍可手动选择其他日期。首页约其他日只能选择一个日期，选定后与景点页使用同一个「设置提醒」检查浮层处理日期资格、授权、提醒名额和支付，不保留独立旧流程。

`FLOW-004` 管理流程：
行程项右侧菜单统一承载标记结果、设置/修改提醒、约其他日、删除行程项。删除单个行程项 / 某日全部行程项均二次确认；行程下无任何行程项时行程消失。提醒任务不再有独立用户入口，14 天清理仍由后台执行。**提醒状态本身不是菜单项**——它在卡片上直显，只有 `未送达` 是可点的（点开看原因）。菜单各项的显示条件见 `HOME-RULE-006`。

`FLOW-005` 抢票跳转流程：
行程项预约入口 → 有官方小程序则直跳，失败或无入口则弹 PAGE-002 选择官网 / 公众号 / 复制链接兜底；V1 不提供代抢、余票监控或付费占位。

### 1.6 首页行程状态墙最终口径（2026-09-16）

六个用户可见状态：`待抢票 / 可抢票 / 已约到 / 未抢到 / 待确认 / 免预约`。（变更：2026-09-28 将 `UNMARKED` 的用户可见文案由「未标记」改为「待确认」；2026-09-22 按设计稿**整体换词**，旧值为 `待抢 / 可抢 / 已成 / 未成 / 开过票了`。换的是文案不是语义）

- `待抢票`：未到放票时间。
- `可抢票`：已放票，24 小时内未人工标记。
- `已约到 / 未抢到`：用户人工结果。首次结果只能从空状态写入；4 秒内允许撤销。出行日结束前允许双向更正：`未抢到 ↔ 已约到`，更正后撤销恢复修改前结果。
- `待确认`：已放票超过 24 小时且未人工标记，是中性态，不判失败；到 `visitDate` 23:59 前仍可补标记和进入官方预约。（2026-09-28 由「未标记」改为此文案；**语义不变**，别因为字面像「未抢到」就把它改判成失败）
- `免预约`：固定状态，只进行程，不生成提醒。
- 状态在读取时动态推导，`UNMARKED` 不落库，不依赖后台定时任务。
- 票务状态与提醒送达状态分离，**两轴分居卡片两侧**：提醒状态在**景点名右侧**（以中性灰 chip 为主，四态 `未设提醒 / 待提醒 / 已提醒 / 未送达`），票务状态在**卡片最右侧**（现有彩底 chip）。`未送达` 前置警告色图标（圆圈 + 叹号），同时加深文字、增加浅描边且**整块可点**，点开弹窗看未送达原因；其余三态保持中性灰，若带图标用信息形（圆圈 + i）。**四态不得共用同一枚图标**——警告语义由图标形状承载，局部颜色只提升可见性；不得把整颗提醒 chip 改成票务红/绿底。**正文文案不得出现「已设提醒」**（它同时指 `WAITING` 与 `TRIGGERED`，歧义）。**免预约项不显示提醒状态，也不显示提醒类菜单项**。菜单显示条件见 `HOME-RULE-006`。（变更：2026-09-22 补齐 09-21 删标签留下的缺口——`NOT_SET` 是动作入口、`MISSED` 是异常信号，都不属于「与摘要卡胶囊重复」那一类，详见 `产品分析/2026-09-14-首页行程化改版决策.md` 新增 3.4）
- 行程摘要“门票搞定 N/M”：M = 去重后的预约需求组，同一景点多个备选只算一个；任意日期已约到即该需求完成；免预约项不计入分母，另显示“另有 X 处随到随玩”。
- 首页多行程按开始日期纵向排列，不使用横向 Tab。顶部只有一张最近行程摘要卡；其他行程使用紧凑分段标题（2026-09-21：摘要卡那一趟不重复渲染标题，见 `HOME-RULE-003`）。历史行程统一折叠在页面底部，结束日次日归入历史。进行中行程内的已结束日期组默认折叠，入口置于该趟内容顶部、今天/未来日期之前，见 `HOME-RULE-007`。**行程全部结束后摘要卡不退场**，改展示最近一段过往行程、副标题显示「已结束」，见 `HOME-RULE-008`。

## 第三册 开发实现规范

### 3.1 技术架构

```
前端：微信原生 + Vant Weapp
后端：腾讯云开发（云函数 + 云数据库 NoSQL）
云函数：reminder（行程/时间线/清单/任务/用户，核心）/ spots（查询+状态计算）/ feedback（意见反馈/信息纠错）/ scraper（抓取）/ notifier（推送）/ ics-generator（.ics 生成，2026-08-14 起日历通道下线，保留但前端无调用）
抓取：云函数 Playwright + stealth 插件（V1 仅抓有官网的景点）
```

数据源策略：V1 优先抓取有官网网页版的景点（`hasWebVersion: true`，见 spots.json）；抓取失败云函数告警开发者；前端预留「信息纠错」众包入口。反爬对策（stealth、住宅代理、指纹随机、分时段频率）沿用旧版技术方案，属运维实现细节，不在本说明书展开。

### 3.2 行程规则

- `TRIP-RULE-001` 行程 = { 城市, startDate, endDate }，由首页创建表单创建；无行程时显示创建引导，有行程时进入状态墙。
- `TRIP-RULE-002` 行程创建**或合并**：同城市即合并成同一行程，日期取并集；新行程可能同时与多个既有行程合并，滚雪球式反复合并直到不再变化。**不存在“一个月没有新建行程才算新行程”的冷却期，也不按日期间隔拆成多趟**。示例：北京 5.31-6.4 + 6.5-6.8 合并为「北京 5.31-6.8」；北京 5.31-6.4 + 6.6-6.8 同样合并。是否属于当前行程只按 `endDate >= 北京今天` 判断，结束日次日进入历史。
  - **合并的是行程（任务分组），不是景点**：每个景点保留自己被选中时的日期段，存为 `spots: [{spotId, startDate, endDate}]`（`spotIds` 降级为 `spots` 的去重派生字段，供想去列表 / 批量查询用）。所以「北京 9.23-9.24 选故宫 + 北京 9.25-9.26 选国博」合并后：行程 = 北京 9.23-9.26（一个 Tab），时间线 = 故宫 9.23/9.24 + 国博 9.25/9.26，**不会**冒出「故宫 9.25」「国博 9.23」——这正是 08-31 取消合并想避免的问题，现由 `spots` 段解决，无需再牺牲分组。
  - 被吞并行程的任务与提醒清单自动改挂到存续行程（提醒本身不受影响），存续行程复用第一个被合并行程的 tripId，用户无感。
  - 老数据兼容：只有 `spotIds` 的行程按行程整段回退（`normalizeSpots`），与合并前口径等价，线上已有行程无需数据迁移。
  - `adjustTripId`（「在当前内联时间线的行程上重新生成」）：该行程的景点段按本次输入**替换**（而非并集），其余被并进来的行程段保留；只要同城，仍会与其它既有行程继续合并。
- `TRIP-RULE-003` 行程命名 = 城市 + 日期范围（如「北京 5.31-6.4」），系统自动生成，用户不可编辑。
- `TRIP-RULE-004` 行程删除判定（V2 覆盖旧任务口径）：只按是否还有 `trip_items` 判断。删除行程项 / 删除某日全部行程项后，行程下无任何行程项则行程消失；草稿时间线尚未提交时，行程可由创建流程管理，不再靠任务数决定。旧任务级联代码仅作迁移期兼容。
- `TRIP-RULE-005` 行程排序：按开始日期升序。
- `TRIP-RULE-006` 多行程呈现（V2 覆盖）：不设分组 Tab，按开始日期纵向分段；每段使用紧凑标题，顶部只有最近行程一张完整摘要卡。

### 3.3 时间线生成规则

- `TIMELINE-RULE-001` 事件生成（**交叉积，但按景点自己的日期段**）：对行程内每个已选景点 S（规则 R = releaseSlots / 兼容旧 advanceDays、releaseTime、closedDays）× **该景点自己的日期段**（`spots` 里的 startDate..endDate；老数据无 `spots` 时回退为行程整段）内每个非闭馆日 D，生成一个候选项：visitDate = D。每个候选携带 `releaseSlots`，表示该出行日全部放票时段；`releaseAt` 取当前最近的未来时段，全部已过时取最早时段用于展示。旧规则没有 `releaseSlots` 时继续按 `releaseTime/releaseTimes` 展开。免预约景点和需预约但无固定放票时刻的景点（如环球影城）生成 `releaseAt=null` 的仅行程候选，不生成提醒任务。事件总数 = Σ(每景点在自己段内的非闭馆日数)，不是时段数；时段只决定该事件下创建几条任务。⚠️（变更：2026-09-24）被跳过的日期和全闭馆景点**不再有任何底部提示**，见 `PAGE-005-RULE-002`。用户通过视图 Tab 选择实际要哪一天，产品不替用户推断出行日（变更：2026-08-04 原规则取「范围内第一个非闭馆日」，导致 N 个景点的提醒全部指向行程首日，用户无法表达「哪天去哪个景点」且无修改入口，会抢到错误日期的票）。（变更：2026-09-14 改为按景点自己的段生成——行程合并后不再把「整段 × 全部景点」做交叉积；2026-10-28 无固定放票时刻的需预约景点也进入时间线并按日期加入行程；2026-11-05 多放票时段改为一条事件下挂多条任务）
- `TIMELINE-RULE-002` **生成是纯预览**（变更：2026-09-20，推翻旧口径）：`timeline.preview` 只按**当前所选日期段与景点**独立计算，不创建、不改写任何行程。
  - **读什么、不读什么（这条界线必须分清）**：
    - **读**：当前用户的**暂存清单**（`reminder_cart` 的 `__pending__` 那一批）。这是用户正在这一页做的、还没提交的工作，不反映它按钮就像坏的——点了「加入清单」页面毫无变化，按钮还写「添加提醒」，再点一次又提示「已经在清单里啦」。
    - **不读**：`trip_items` 与 `reminder_tasks`。那是别的行程的既成事实，读它就会把历史状态带进预览——换一批日期重新生成时，用户看到一条标着「已在行程」的日期，其实属于另一趟行程。
  - 因此**纯预览里不会出现「已在行程」**（代价见下条）；重复加入由 `cart.add` 按 `(userId, spotId, visitDate)` 跨行程兜底拦截。
  - **代价（已确认接受）**：预览里看不到「已在行程」。同一 `(spotId, visitDate)` 重复加入由 `cart.add` 的去重拦截（它按 `(userId, spotId, visitDate)` 跨行程查）。
  - **行程创建与合并判定（TRIP-RULE-002）挪到提交清单时执行**；老口径 `adjustTripId`（在当前行程上重新生成＝替换景点段）**废止**。
  - 日期段或景点一变，已有预览即作废，须重新生成。
- `TIMELINE-RULE-003` 视图（二者均为**单选筛选**，一次只显示选中项下的事件，不同屏平铺全部交叉积）：按出发日 = 以 visitDate 为 Tab，选中某日 → 显示该日全部景点的放票事件，组内按 releaseAt 升序；按景点 = 以 spot 为 Tab，选中某景点 → 显示该景点在各出行日的放票事件，组内按 releaseAt 升序。
- `TIMELINE-RULE-004` 事件状态判定（**三态选择机 + 两个时间状态**）：按钮只看选择状态——未加入 → 「加入清单」，在清单 → 「已加清单」，已提交 → 「已加行程」；顶部时间状态看 releaseAt——未到点「待开票」、已到点「已开票」、免预约「无需预约」。`releaseAt ≤ now` **只改变展示，不提供预约入口，也不能把按钮变成 BOOKABLE/FULL**。（变更：2026-09-25；详见 PAGE-005）
- `TIMELINE-RULE-005` 闭馆日（**按日判定**）：某景点在某日闭馆 → 该 (景点, 日) 不生成事件，其余日期照常生成；若该景点在行程范围内每一天都闭馆，则完全不生成事件。（变更：2026-09-24 删去「想去列表该行标注『行程期间闭馆』」——见 `PAGE-005-RULE-002` 的「静默」口径）
- `PAGE-005-RULE-002`（2026-09-24）**时间线不承载行程级信息，被跳过的日期零提示**：
  - **不再有任何底部提示块**。原文两处产出——① 非全闭馆景点被跳过的日期（`closedDaySkips`，「9月28日（周一）、10月5日（周一）闭馆，已为你跳过」）、② 行程内全闭馆的景点（`closedSpots`）——**都不再渲染**。无固定放票时刻的景点已改为可加入行程的候选，不再归入 `closedSpots`。
  - **判定与生成逻辑不变**：该跳的日期照跳、不生成事件，事件列表与改前逐条一致。删的只是展示。
  - **三条理由**（缺一条都别把它加回来）：
    1. 行程一跨周一，**每个景点都必然有一行**（跨 3 个周一 = 6 个景点 6 行）→ 恒定噪音块，不长在任何状态上；
    2. 与 2026-09-20 决策「同类信息不再在时间线下方单独堆叠成区」同一条口径（那次删的是免预约区块）；
    3. 用户不会拿「跳过了哪天」做决策：行程定死、景点定死，跳过哪几天是客观结果，不是可操作信息。它是**行程级**的，而这个页面的职责是挑选日期。
  - 行程内**每一天都闭馆**的景点同样静默——决策文档 4.3 第 4 条「用户没设备选、行程内也没有可用日期：静默，不予任何提示」。
  - ⚠️ **服务端返回值不缩水**：`timeline.preview` 的 `closedSpots` / `closedDaySkips` 照常返回（数据契约不变、已有测试继续钉住），只是页面不消费。要恢复提示时不必改云函数。


### 3.4 提醒清单规则

- `CART-RULE-001` 清单是提交缓冲区：加入 / 删除 / 清空只改缓冲区，不创建任务、不写 ICS。
- `CART-RULE-002` 聚合展示：「已选 N 项，覆盖 M 个景点」，N=清单条数，M=去重景点数。
- `CART-RULE-003` 清单持久化：按用户存云数据库（TABLE-007），在**同一时间线范围内**跨设备 / 重启不丢；提交成功后对应条目清除。生成新时间线时，不再属于本次日期段或景点集合的条目自动移除（见 `CART-RULE-007`）。
- `CART-RULE-004` 一键全部提醒：**仅作用于当前选中的 Tab**，不跨 Tab 批量。按钮文案为「一键全部提醒」，加入该日全部 SELECTABLE 事件；景点视图下为「该景点全部提醒」，加入该景点各出行日的全部 SELECTABLE 事件（适用于「哪天都行、先都提醒着」）。禁止一次加入整条时间线的交叉积（变更：2026-08-04 随 TIMELINE-RULE-001 改为交叉积，原文「当前时间线下所有 SELECTABLE」会一次加入数十条，等于替用户决定每个景点都去每一天）。

- `CART-RULE-005` 入口：首页内联时间线底部清单条 icon 打开 PAGE-007 弹窗（当前实现为 cart-popup 组件）。（变更：2026-08-26 PAGE-005/006 已并入首页）

- `CART-RULE-007`（2026-10-28）**清单只承载当前这次生成的时间线**：PAGE-005 每次生成成功后，服务端把暂存清单收敛到本次 `startDate ~ endDate × spotIds` 范围；范围外的历史草稿自动移除，范围相同则保留原草稿。只清理暂存区，真实 `tripId` 下的旧链路清单不动。这样用户换日期/景点重新生成后，不会在 PAGE-007 看到上一批项并被一起提交。

### 3.5 提醒任务规则

- `REMINDER-RULE-001` 提醒时间点 = releaseAt − offset，offset ∈ 用户勾选的提前量（5 分钟 / 2 分钟，单选二选一；一次性订阅消息按条授权，一条任务只发一条提醒）。当前清华只保留即时预约，工作日提前 1 天 `08:00`、周六周日及法定节假日提前 7 天 `08:00`；军博只保留最早 `08:00`。两个景点每个出行日都只创建 1 条任务，任务仍挂 `itemId` 并以 `releaseKey` 稳定识别。底层 `supportsMultiRelease=true` 时仍可按 `releaseSlots` 创建多任务，但当前种子数据不得配置多个时段。未声明能力的旧客户端继续按顶层 `advanceDays + releaseTime` 创建单任务。清华“周末”口径同时包含法定节假日，节假日日期只取用户确认或官方已公布范围。订阅授权与提醒名额按实际任务总数计算。
- `REMINDER-RULE-002` 通道：公众号订阅消息。手机日历 ICS 已于 2026-08-14 下线（ICS-RULE 保留为遗留规则），短信 V1.1。任务创建时写入 `templateId`：新任务使用「预约开始提醒」，旧任务没有该字段时继续使用旧「活动开始通知」模板，避免切换模板影响存量待提醒。（变更：2026-08-26 标注日历通道下线；2026-10-01 增加模板兼容）
- `REMINDER-RULE-003` 错峰推送：同一放票时间点的批量任务在 30 秒窗口内错峰发送，避免官方接口拥堵。
- `REMINDER-RULE-004` 状态写入：实际发送成功 → TRIGGERED；超过 releaseAt 仍未成功 → MISSED；发送失败不记 sentOffsets，下一分钟重试；前端「已过期」筛选包含 MISSED；UI 标签：TRIGGERED「已提醒」，MISSED「未送达」。（2026-09-14 补：① 「已过 releaseAt 仍是 WAITING」在读取时即视为 MISSED，`task.list` 兜底补判并落库，不再依赖 notifier 定时链路必须成功；② 发送失败原因写入 `lastSendError`，sweepMissed 优先用它当 `missedReason`，避免「WX_APPSECRET 未配置」「43101 配额不足」这类可行动信息被笼统文案盖掉；③ notifier 的 tick 三步互相隔离，`scanAndSend` 抛错不再连带 `sweepMissed` 不执行）
- `REMINDER-RULE-005` 任务删除（变更：2026-09-20 按行程项删除口径重写）：**用户不对提醒任务直接操作**，任务随其所属行程项一并删除。
  - 删行程项（单个或某日全部）→ 连带删除其名下**全部**任务，含 TRIGGERED。
  - 旧口径「已送达的提醒保留为历史、不许删」与收束动线冲突，已废止——用户标了「抢到了」要删掉备选，却因为那条提醒已送达而删不干净，是说不通的。
  - **提醒额度不退还**：删任务时微信那边的授权次数已经花掉，账本不回调。
  - 后台仍按 `REMINDER-RULE-006` 做 14 天自动清理。
- `REMINDER-RULE-006` 自动清理：任务进入 TRIGGERED / MISSED 后 14 天自动删除（CLOSED），触发行程级联检查（TRIP-RULE-004）。
- `REMINDER-RULE-007` Tab 角标（已废弃 2026-08-20）：原定义为未来 24 小时内 WAITING 任务数。因 2 栏 tab、首页直达任务列表，角标与「进行中 N」口径不一致易造成困惑，已整体移除（含 `task.badge` 接口），规则号保留避免后续编号级联。

- `REMINDER-RULE-009`（2026-09-29）**订阅授权补齐入口分层**：
  - `PAGE-008` 主流程继续执行授权硬闸门：额度不足时主按钮禁用，用户必须主动点击「点击补授权次数」，不得自动补齐，也不提供「仅加行程」旁路。一次点击只申请 1 条额度；需要 N 条就进行 N 次用户点击。不得用异步串行伪造“一次点击补满”，该调用会脱离用户手势上下文并被微信拒绝。
  - 景点卡片、景点详情、分享场景和首页「约其他日」在订阅额度不足时，不跳「提醒设置」页。使用固定底部「设置提醒」浮层，同时展示本次需要、当前可用、待发送占用和还差次数；PAGE-008 同款固定按钮「点击补授权次数」每次用户点击只发起一次微信订阅。若仍不足，浮层保持打开并刷新缺口；补足后不自动提交，用户点击「开启行程放票提醒」继续。禁止自动连发授权，禁止逐次重新弹出系统 ActionSheet。首页仍只选择一个日期，其余授权与名额流程完全复用景点页。
  - 判定「额度不足」时必须使用**当前可用授权** = 台账剩余授权次数 − 未来待发送提醒消息数。已排队的 `WAITING` 任务还没发送，但已经占用了微信一次性订阅次数；只比较台账总数会导致新增提醒重复承诺同一笔授权。首页开启提醒、景点卡片「设提醒」、PAGE-008 必须同一口径。
- 轻量入口仍可让用户选择「仅加行程·不提醒」或取消；只有微信通知权限未开启、订阅消息总开关关闭或历史选择仍为拒收时，才打开系统/微信设置引导。禁止用「补授权次数+1」页替代本次流程。
- 景点卡片、景点详情和分享场景使用一个标题固定为「设置提醒」的统一浮层，视觉和信息结构与 PAGE-008 同构：上方根据 `cart.planQuickDates` 展示日期资格拆分，然后复制放票提醒授权区、固定补授权按钮、三条授权说明与提醒样式入口；下方仅在服务端 `enforced=true` 且名额不足时展示提醒名额区。两个硬闸门在同一浮层内同时检测，不再拆成两个浮层。
- 全部选中日期都已过放票时间或只能加入行程时，不得自动提交或只弹 Toast：浮层持续展示原因，主操作为「仅加入行程」，另提供「重新选择日期」。部分日期失效时先展示“N 天可提醒、M 天仅加入行程”，用户确认后才提交；授权与名额只按可提醒日期计算。
- 无名额限制且授权满足时底部显示「开启行程放票提醒」；有名额限制时底部按钮置灰，名额卡主按钮显示服务端生成的「支付 X，购买会员/提醒名额并继续」。支付由服务端确认权益到账后，自动用本次原 `spotId/visitDates` 重提并反馈提醒设置结果；若授权仍有缺口，则保留浮层并引导补齐。另行点击「查看会员权益与退款说明」只进入会员页，不发起支付。支付取消或失败时保留本次日期；快捷入口不写主流程临时清单，关闭浮层无需清理。

### 3.8 页面生命周期

- 首页 onShow：在自适应复用窗口内直接使用本地缓存；过期后才调用 `home.bootstrap` V2。放票前 60 分钟至放票后 10 分钟为 30 秒，今天仍有后续放票为 60 秒，其余时段为 5 分钟。用户下拉刷新、冷启动和写操作后始终立即请求。若用户从推送进入，滚动定位对应 `itemId`。
- 首页「添加提醒」视图（不单独建页）：生成时间线后保留内联进度；行程或想去列表变化 → TIMELINE-RULE-002 重算，否则用缓存。
- 时间线倒计时：前端本地秒级倒计时，基准为服务端 GMT+8 时间戳（进入页面时校时一次）。
- 提交页提交中：按钮 Loading「正在为您查询…」风格，防重复提交。
- 我的页 onShow：优先使用 5 分钟内的 `user.bootstrap` 结果刷新会员、提醒名额和通知授权状态；管理端能力探测单独缓存 24 小时。

### 3.11 首页行程化 V2 规则（覆盖冲突旧条目，2026-09-16）

- `TRIP-ITEM-RULE-001` 行程项 = `{ tripId, spotId, visitDate }`，逻辑唯一；同一景点多个备选日期各为一个行程项，共用一个 `backupGroupId`。
- `TRIP-ITEM-RULE-002` 行程项是首页状态墙、票务进度、提醒任务和删除动线的事实来源；行程为空只看是否还有行程项。
- `TRIP-ITEM-RULE-003` 状态在读取时推导：`result` 只持久化人工结果，`UNMARKED` 不落库；放票后 24 小时转“待确认”。
- `TRIP-ITEM-RULE-004` 人工结果只能从空状态写一次，**4 秒**内可通过 `tripItem.undoResult` 撤销；之后不可修改。（变更：2026-09-17 由 10 秒收紧为 4 秒——误触判断不需要 10 秒，4 秒足够且更快锁定结果）
- `TRIP-ITEM-RULE-005` 放票后官方预约入口持续保留到 `visitDate` 23:59，不因进入“待确认”或标记“未抢到”而消失。
- `TRIP-ITEM-RULE-006` 抢到后若有备选：用户删则删除对应行程项及任务；用户保留或不操作则继续按原计划抢票和提醒。
- `TRIP-ITEM-RULE-007` 没抢到后已有可用备选时提升下一备选；没有时展示候选日。候选只判断开放和是否已放票，不承诺实时有余票。
- `TRIP-ITEM-RULE-008` 进度分母按预约需求组去重；同一 `backupGroupId` 内任意行程项已约到即完成该组，免预约项不计入分母。
- `TRIP-ITEM-RULE-009` 多行程按开始日期纵向分段，不设横向 Tab。顶部只有最近行程全局摘要卡；其他未结束行程使用紧凑分段标题（摘要卡那趟不重复渲染标题，见 `HOME-RULE-003`）。历史行程结束日次日读取时归入底部折叠区。
- `TRIP-ITEM-RULE-010` 提醒送达状态 `NOT_SET / WAITING / TRIGGERED / MISSED` 与票务状态分离；MISSED 必须显示轻量警告 icon 和原因入口。
- `TIMELINE-RULE-001` 的新增补充：免预约景点也进入排期时间线并按日期加入行程，但不生成释放事件和提醒。环球影城同理，可加入行程和查看安排，但不可设提醒。（变更：2026-10-28）
- `CART-RULE` 的新增补充：购物车项包含 `remindOn`；强提醒（含 `strongReminder=true`）默认勾选，弱提醒默认不勾，免预约项固定无提醒。全部不提醒时直接提交；存在提醒项时进入 PAGE-008 后统一提交。
- `REMINDER-RULE` 的新增补充：提醒任务必须挂 `itemId`；用户不再通过任务列表管理提醒。已有任务的票务结果与提醒送达状态必须分开展示。
- `CART-RULE-006`（变更：2026-09-20）**清单是提交前的暂存区**：没提交之前暂存在清单页里（退出、切后台都还在），提交（`cart.commit`）之后立即清空。不引入临时/草稿行程、不设失效期。用户显式删掉最后一笔已落库行程项后，失去归属的暂存清单一并清空；账号仍有其他行程项时不误删草稿。（2026-09-29）
- `TRIP-RULE-002` 的补充（2026-09-20）：行程的**创建与合并判定改在 `cart.commit` 时执行**——纯预览化后「生成时间线」不再建行程。各景点的日期段由它自己的 `visitDate` 集合推导（`故宫 10.2+10.3 → 故宫 10.2-10.3`），合并后不互相膨胀。
- `HOME-RULE-003`（2026-09-21）**摘要卡补齐「未来行程」；行程分段标题整条删除**：
  - 摘要卡底部展示**「即将提醒」胶囊**（设计稿 UI/V.0.2-0919）：最多 **2 个**接下来要放票的**时间点**，格式「今天20:00 城楼/国博」/「9月24日 20:00 故宫」（**末尾不带「放票」**——胶囊本身已在「即将提醒」语义下，重复是白占两个字宽度）。点胶囊打开该景点详情浮窗（预约入口 + 倒计时）。

  - **行程分段标题（`北京 9月30日 ~ 10月3日 搞定 0/3`）按 `weak` 取舍——不是一刀切**。判据是「这一段是不是顶部摘要卡那一趟」：
    - **摘要卡那趟**（`trips[0]`）：标题行与摘要卡是同一趟的同一批信息（城市、日期范围、进度），同屏重复 → **不渲染**。
    - **后面还没发生的行程**：摘要卡只展示最近即将发生或正在发生的那一趟，**没有覆盖它们**，所以**必须渲染**标题行——否则那一段会直接塌成一堆裸日期，用户读不出「这是独立的一段、到哪结束」。
    - ⚠️「未来行程」那行小字是摘要卡上的**指路**，**不是这个标题行的替代品**：小字没有进度，也不承载分段的视觉边界。**别因为它存在就把标题行删掉。**

    - **连带失效**：① 行程分段标题的**吸顶**（吸顶本就是为这一行做的，模板里的 `ts-spacer` 撑高占位、组件三个吸顶属性、以及页面每次滚动一轮 `boundingClientRect` 的 `measureSections` 全部删除——留着就是空跑查询）；② 只为该行计算的数据（`dateRange` / `progressText` / `weak`）与其样式（`.ts-city` / `.ts-range` / `.ts-progress` / `.ts-manage`）。
    - 日期菜单的键由 `tripId|visitDate` 复合键简化为**纯 `visitDate`**（分段标题没了就无需把 tripId 编进键里）。⚠️ 页面 `onDateMenu` 与组件 `menuOpen` 两处算法必须逐字一致，否则点菜单不展开且不报错。

### 3.12 分享体系规则（2026-09-25）

### TABLE-003 spots（景点表）

沿用 `data/spots.json` 结构：spotId, name, **shortName**, category, district, address, location, officialAppid, officialPath, officialWebUrl, difficultyScore, popularityScore, reservationRequired, **strongReminder**, aliases, hasWebVersion, scrapingUrl。`reservationRequired`：是否仍需实名预约（false = 免预约，可进入时间线和行程项、不进提醒流程，卡片按钮显示「加入行程」，标签行显示 `cardDesc`「随到随买，当前{旺季/淡季}门票…」，难度标签不渲染）。`strongReminder`：显式将难度 ≤2 的需预约景点提升为强提醒；仅影响提醒文案与默认勾选，不改难度，也不改变放票规则。卡片接口另派生 `addable` / `remindable` / `weak`：`addable` = 所有景点均可加入行程；`remindable` = 需预约且有放票时刻（18 个，可设提醒并生成提醒任务）；`weak` = 需预约、difficultyScore≤2 且未设置 `strongReminder=true`（5 个可提醒景点：八达岭/科技馆/美术馆/慕田峪/天文馆，标签行显示「提前N天 HH:MM放票 · 票量充足，无需卡点」）；需预约但无放票时刻（仅环球影城）`addable=true`、`remindable=false`，卡片显示「随买随用」且可选择，时间线按钮为「加入行程」，只落行程项、不创建提醒任务。（变更：2026-08-26 新增 remindable/weak 口径；2026-08-31 难度 V2 后 weak 由 4 增至 13；2026-09-15 V3 后 weak 为 11；2026-10-28 新增 strongReminder，6 个景点移出弱提醒后 weak 为 5；同日 addable 改为全景点可加入行程）

### 枚举与状态机

- `ENUM-001` TripStatus：ACTIVE（进行中）/ FINISHED（已完成）。**完成判据看行程项，不看提醒任务**——否则只有免预约景点、没设提醒的行程会被误判成空行程。实际归入历史由 `endDate` 在读取时判定，不依赖定时任务。（变更：2026-09-20）
- `ENUM-002` ReminderBackendStatus：WAITING / TRIGGERED / MISSED / CLOSED。
- `ENUM-003` EventSelectStatus（时间线按钮态）：SELECTABLE / IN_CART / COMMITTED。其中 COMMITTED 表示该 `(spotId, visitDate)` 已落 `trip_items`、不可重复加入。
  （变更：2026-09-20 ① 废止 `BOOKABLE` / `FULL`——时间线回归纯挑选职责，不再提供预约入口；两者保留于 `ENUM-005` 实时放票状态。② 删除 `WAITING` / `REMINDERED`——那是旧任务列表的按钮态，首页行程化后时间线不再承载任务态。③ `timeline.preview` 默认不读已落库状态；只有传入 `committedTripId` 时读取**这一趟**已有的 `trip_items` 并返回 `COMMITTED`。2026-09-25 起 `ENUM-003` 最终只保留 `SELECTABLE / IN_CART / COMMITTED`）
- `ENUM-004` ChannelType：OFFICIAL_ACCOUNT / SMS（reserved）。CALENDAR_ICS 已于 2026-08-14 移除。（变更：2026-08-26 与 API-契约对齐）
- `ENUM-005` ReleaseStatus（实时放票状态）：NOT_RELEASED / BOOKABLE / FULL。
- `ENUM-007` TicketState（行程项展示态）：PENDING / BOOKABLE / SUCCESS / FAILED / UNMARKED / NO_RESERVATION，依次对应「待抢票 / 可抢票 / 已约到 / 未抢到 / 待确认 / 免预约」。（变更：2026-09-28 `UNMARKED` 用户可见文案由「未标记」改为「待确认」；2026-09-22 按设计稿整体换词，旧值为 `待抢 / 可抢 / 已成 / 未成 / 开过票了`。文案真身在 `cloudfunctions/reminder/lib/item.js` 的 `TICKET_STATE_LABEL`，`miniprogram/utils/mock.js` 是镜像，`test/mock-mirror.test.js` 交叉比对）
- `ENUM-008` TicketResult（人工结果）：SUCCESS / FAILED；null = 未标记。
- `ENUM-009` ReminderDeliveryState（提醒送达）：NOT_SET / WAITING / TRIGGERED / MISSED，与票务状态分离。
- `ENUM-006` DifficultyLabel：三挡，与 TAG-RULE-001 同一阈值 —— EXTREME(difficultyScore ≥4)「极难约」/ NORMAL(=3)「较难约」/ EASY(≤2)「容易约」。注：现有 26 个景点 difficultyScore 取值 {1,2,3,4,5}；B 层免预约（reservationRequired=false）景点 difficultyScore 不统一（首博、孔庙国子监为 2，其余为 1），UI 不渲染难度标签。

- `STATE-001` 后台提醒状态机：WAITING →（发送成功）TRIGGERED →（+14d）CLOSED；WAITING →（超时未触发）MISSED →（+14d）CLOSED；WAITING →（用户删除）直接物理删除。
- `STATE-002` UI 状态映射：NOT_SET → 「未设提醒」；WAITING → 「待提醒」；TRIGGERED → 「已提醒」；MISSED → 「未送达」（附原因解释入口）；CLOSED → 不展示。**判定口径单一**：`backendStatus` 是唯一真身，「已过 releaseAt 的 WAITING」在返回前已被收敛为 MISSED，前端不再自行按时间推算状态（否则会出现「已过期 + 待提醒 + 无图标」的三方不一致）。**四态在行程项卡上的呈现口径见 `HOME-RULE-006`**——`未送达` 用警告形图标（圆圈 + 叹号）且可点，其余用信息形；**不得让 MISSED 与 WAITING 长得一样**。（变更：2026-09-14；2026-09-22 补 NOT_SET 与卡上呈现口径）
- `STATE-003` 选择状态机：SELECTABLE →（加入清单）IN_CART →（提交）COMMITTED；IN_CART / COMMITTED 均不可再次选择。
  （变更：2026-09-20 删除 `WAITING` / `REMINDERED` 与 `BOOKABLE →「立即预约」`；2026-09-25 同步删除 `FULL`——预约入口只保留在首页行程卡片与推送落地的详情浮窗，时间线本身不再有第四态。已开票项仍走 `SELECTABLE → IN_CART → COMMITTED`，只在顶部显示「已开票」。清单是**提交前的暂存区**，提交即消费）
- `STATE-004` 行程项票务状态机：`NO_RESERVATION`（免预约）｜`PENDING`（未到 releaseAt）｜`BOOKABLE`（releaseAt 到达且 24h 内未标记）｜`UNMARKED`（超过 24h 未标记，展示为待确认）｜`SUCCESS` / `FAILED`（人工结果）。状态读取时推导，UNMARKED 不落库。
  推导放在**唯一一处** `cloudfunctions/reminder/lib/item.js`，判定顺序固定为 免预约 → 人工结果 → 放票前 → 放票后 24h 内 → 待确认；页面不得自行按时间再推一遍。（变更：2026-09-20 明确单一真身与顺序；2026-09-28 更新 UNMARKED 展示文案）
  **文案（2026-09-28 更新）**：`免预约 / 待抢票 / 可抢票 / 待确认 / 已约到 / 未抢到`。⚠️ `UNMARKED` 的文案是「待确认」，但它的**语义仍是中性态、不判失败**——别因为字面像「未抢到」就把它改判。
- `STATE-005` 人工结果状态机：`null` →（抢到了）SUCCESS 或（没抢到）FAILED；**4 秒**内可撤销回 null；超时后首次结果不可修改。出行日结束前允许从首页右侧菜单双向更正：`FAILED → SUCCESS`（「已抢到」）或 `SUCCESS → FAILED`（「未约到」）；更正后 4 秒内撤销恢复修改前结果。（变更：2026-09-17 由 10 秒收紧为 4 秒）
